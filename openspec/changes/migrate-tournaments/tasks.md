## 2. Tournament creation, record, and structure (Convex — `packages/convex-snek-platform/`, auth wrapper in `packages/convex-host/`)

- [ ] 2.1 Add the tournament, round and match tables to the platform component schema: the tournament carrying its three meta-parameters, its own lifecycle state (including halted), its fixed participant set and its captured base gameplay configuration; a round carrying its ordinal and its **set** of matches; a match carrying its room, its teams and its **sequence** of games; and the back-references a game needs to name the match it belongs to. Shape both collections as collections from the start — a single match per round and a single game per match must be one member of a set, never a scalar field a later parallel-match round would have to migrate (`tournaments/round-structure`, `tournaments/round-structure#a-second-match-reshapes-nothing`)
- [ ] 2.2 `createTournament` as one transaction: validate all three meta-parameters as required and in range (rounds 1–16, interlude 0–120 minutes, scheduled start strictly in the future), reject with the offending parameter named, and commit the tournament record together with the room of each opening-round match — created through the room capability's own creation path with the calling user as owner, not a second room-creation path of this change's own (`tournaments/tournament-creation`, `#every-meta-parameter-is-required`, `#created-with-its-settings`, `#a-start-already-past-is-refused`, `rooms-and-matchmaking/room-creation`)
- [ ] 2.3 Mark the rooms a tournament creates as governed by it, so the room capability's guard refuses the acts a format reserves — enrolment change, manual start, archival — while leaving configuration and abdication open to the owner during the wait. The marking is what that guard reads, so setting and clearing it is this capability's half and the refusal is the room capability's: every room the tournament creates stays governed for the tournament's whole lifetime — a completed round's room included, long after its match is over — and is released only when the event concludes or halts (`tournaments/round-structure`, `rooms-and-matchmaking/room-administration#reserved-acts-belong-to-the-governing-format`, `rooms-and-matchmaking/room-archival#archive-blocked-mid-play`)
- [ ] 2.4 Fix the participant set at the moment the tournament begins: snapshot the teams then enrolled in the opening round's rooms, **excluding any archived at that moment**, and capture the opening round's first game's gameplay configuration as the base every later game is built from (`tournaments/round-structure`, `tournaments/round-structure#archived-teams-are-not-participants`, `tournaments/round-config-inheritance`, `team-management/archive-not-delete`)
- [ ] 2.5 Round and match creation copies the captured base configuration into each new game's own record — never a live read of any game record — and carries no tournament meta-parameter into it, so a game's finish chains inside its tournament instead of spawning a nested one; each created game is a full game record served by its own freshly provisioned instance, inheriting nothing of its predecessor's per-game state, with the provisioning and teardown bracket itself `game-lifecycle`'s and consumed rather than reimplemented (`tournaments/round-config-inheritance#identical-play-round-to-round`, `#no-nested-tournament`, `#the-capture-closes-the-editing-window`, `tournaments/round-structure#every-round-a-real-game`)
- [ ] 2.6 A forfeit is scoped to its game: the next round's start invites every participant's server again from the tournament's participant set, never from the previous round's seated set (`tournaments/round-structure#forfeit-does-not-unseat`)

## 3. Round scheduling and chaining (Convex — `packages/convex-host/` orchestration and finish handler)

- [ ] 3.1 Defer the opening round to its scheduled moment and no later: the tournament sits with its rooms configurable until that instant, then begins on the platform's own act with readiness accelerating nothing and nobody's absence deferring it (`tournaments/round-scheduling#never-before-the-scheduled-moment`, `#the-bell-does-not-wait`)
- [ ] 3.2 Chain rounds from the finish handler: on a round finishing with rounds remaining, schedule the next round's creation and start after the configured interlude has elapsed, as the platform's own act with no captain, room owner, or admin able to initiate it. Creating a round means creating its matches, **their own rooms** — through the same governed-room path as 2.2–2.3 — and their games together: a later round is contested in a room of its own, not in the opening round's room playing again (`tournaments/round-scheduling#interlude-then-the-platform-acts`, `tournaments/round-structure`, `rooms-and-matchmaking/room-creation#a-formats-room-is-an-ordinary-room`)
- [ ] 3.3 Give every game of a tournament — the opening round's included — a start path that consults no readiness declaration and takes no user initiation, deliberately not a reuse of the manual start path whose readiness gate no scheduled game could ever satisfy; assert that the room's gate is never entered on this path (`tournaments/round-scheduling`, `#no-ready-check-between-rounds`, `rooms-and-matchmaking/game-start-gate#a-scheduled-start-does-not-consult-this-gate`)
- [ ] 3.4 Suppress the default successor auto-creation in every tournament room from the first round onward, not only after the last — the tournament's own chaining is what creates the next contest, and an intermediate round's room left to the default is handed a stray successor nobody will play. At the final round the succession simply ends: the tournament concludes, creates nothing further, and releases its rooms per 2.3, making concrete the format-governed arm of successor auto-creation. **Seam to settle before implementing**: a room whose current game is finished with no successor is still *playing* by the room capability's own mode rule, which would leave a concluded event's rooms permanently unarchivable — the opposite of the release this scenario promises. Agree the resolution with `migrate-rooms-and-matchmaking` rather than picking one in code (`tournaments/round-scheduling#nothing-after-the-final-round`, `game-lifecycle/successor-auto-creation`, `rooms-and-matchmaking/room-mode#configuring-resumes-with-the-successor`, `rooms-and-matchmaking/room-archival#archive-blocked-mid-play`)
- [ ] 3.5 Make Convex the sole scheduling authority in the implementation and not only in intent: the scheduling state and the chaining trigger live in the platform, never in a finishing round's instance; scheduled work survives deployment restarts, and a round is never double-created or double-started (`tournaments/round-scheduling`)

## 4. Schedule-bound starts, absences, and the stall (Convex)

- [ ] 4.1 Mark a tournament game's start as schedule-bound so the launch gates take their override arm: recorded server health is ignored at the scheduled moment, and a server that refuses or fails to answer within the invitation window costs its team the seat instead of aborting the launch (`tournaments/scheduled-start-override#unhealthy-is-ignored-at-the-bell`, `#refusal-costs-the-seat-not-the-round`, `game-lifecycle/launch-gates`)
- [ ] 4.2 Branch on the acceptance count once every invitation has resolved — two or more seated teams play, exactly one is a walkover, zero is a no-contest — entirely inside the game's own start orchestration, with no retry-until-healthy loop anywhere on the path. The straight-to-finished transition the last two branches take is `game-lifecycle`'s and is consumed, not re-derived here; what this capability supplies is the branch condition and the outcome written on it (`tournaments/scheduled-start-override#bounded-resolution`, `tournaments/walkover-and-no-contest`, `game-lifecycle/status-authority#walkover-straight-to-finished`)
- [ ] 4.3 Author the walkover and no-contest outcomes in Convex for a game no turn ever resolved: the sole seated team a win with the plain score 1.0, every other participant a marked forfeiter, and no winner at all on a no-contest — no sentinel outcome value on any branch, and the value written directly rather than by invoking the engine's formula on an unplayed game. Both branches must finish with a *recorded outcome*, no-contest included: a game decided without play is listed and counted downstream exactly like any other, and one left outcome-less would instead read as a failed game and vanish from every history, statistic and ranking (`tournaments/walkover-and-no-contest#walkover-scores-par`, `#no-contest-no-winner`, `accounts-and-profiles/recorded-outcomes-only#decided-without-play-still-counts`)
- [ ] 4.4 Record a forfeit as the unseated-teams marking on the game record, with the score taken from the engine's scoring rule and **not** computed a second time here; pin with a test that a team which played to a genuine zero carries no marking, so the marking is the only discriminator (`tournaments/forfeit-scoring`, `#zero-scored-and-marked`, `#marking-not-value-distinguishes`, `game-engine/scoring#forfeit-exclusion`)
- [ ] 4.5 Persist the marking alongside the score on the finished game record and expose it on every read path the presentation surfaces of §7 consume — the game-result projection, the history-listing projection, the leaderboard's game set, the live observation surface's team rows, and the persisted replay — so each of them can report a forfeit as a forfeit without inferring one from a zero and without a second forfeit rule of its own (`tournaments/forfeit-scoring`, `#forfeit-visible-downstream`, `game-lifecycle/game-record`)
- [ ] 4.6 Run chaining identically off a walkover or no-contest round: the interlude runs, the next round is scheduled, and a final round concluded on any branch still ends the tournament (`tournaments/walkover-and-no-contest#chaining-indifferent-to-branch`)
- [ ] 4.7 The stall path: when a round's launch fails for a platform reason — generation, provisioning, initialization, or the orchestration itself — halt the tournament with the failure recorded, leave the round not-started with the instance cleanup that `game-lifecycle` already performs, schedule nothing further, and expose no resume affordance or automatic retry. Test that a halted tournament stays halted after the infrastructure recovers (`tournaments/round-launch-failure`, `#the-stall-is-graceful-and-named`, `#no-self-resumption`, `game-lifecycle/no-orphans`)

## 5. Standings and the event's outcome (Convex)

- [ ] 5.1 Compute a tournament's standing as each participant's running total of the scores its completed games recorded — read from the game records, nothing recomputed, no round weighted differently — and expose it as a query the in-room view reads (`tournaments/event-outcome`, `#standing-is-the-running-total`)
- [ ] 5.2 Determine the winner only at the final round's finish, with participants tied at the top sharing the result and no tiebreak round scheduled; before that moment the query returns a standing and no winner (`tournaments/event-outcome#winner-only-at-the-end`, `#a-tie-at-the-top-is-a-tie`)
- [ ] 5.3 A halted tournament's outcome is indeterminate for good: no winner is ever derived from its partial standing, while the games that did finish keep their records and results unchanged (`tournaments/round-launch-failure#a-halted-event-was-never-won`, `tournaments/event-outcome`)

## 6. Tournament-wide roster freeze (Convex)

- [ ] 6.1 Publish participation in an in-progress tournament as a **freeze source** the existing guard consumes, rather than adding a tournament arm inside that guard or writing a second guard here. `team-management/roster-freeze` is authored to read a fact published by the capability running the engagement and to assemble no answer of its own out of the records behind it, so the seam is: this capability exposes the fact, and `team-management`'s one guard — which stays free of tournament vocabulary — rejects every membership, captaincy and server-nomination mutation for a participating team, reading the source inside the transaction of the mutation it rejects. Note this is a *distinct* source from `game-lifecycle`'s published engagement, which covers only a game in play (`tournaments/tournament-roster-freeze`, `team-management/roster-freeze`, `game-lifecycle/competitive-engagement#published-not-inferred`)
- [ ] 6.2 Anchor the freeze on the tournament's own state rather than on any round being played, from the moment the tournament begins, and cover all three boundaries with tests: a mutation attempted in an interlude is rejected exactly as mid-round, the freeze lifts with no residual hold when the final round finishes, and it lifts equally when the tournament halts. Verify the two composed consequences authored elsewhere and only relied on here — team archival stays blocked for the tournament's whole lifetime, and the freeze reaches every surface's mutations because they share one server-side contract — recording that reasoning as a `// design:` reference rather than restating it (`tournaments/tournament-roster-freeze#anchored-to-the-tournament-not-to-a-round`, `#frozen-through-the-interlude`, `#lifts-when-the-final-round-finishes`, `#a-halt-lifts-it-too`)

## 7. Presentation: the in-room view, and forfeit reporting on the surfaces it reaches (`apps/centaur-server-reference/`, plus diffs to sibling-owned surfaces there and in `packages/centaur-server-lib/`)

- [ ] 7.1 Render the event's state inside the room's own lobby, not on a separate page: which tournament this room belongs to, which round of how many and which match, the teams contesting it, and the results of completed rounds with each round's resolution shown as what it was — played out, a walkover, or a contest nobody entered (`tournaments/tournament-view`, `#orient-without-leaving-the-room`, `rooms-and-matchmaking/room-lobby`)
- [ ] 7.2 Show the standing and what comes next: each participant's current total, and either the moment the next round begins, or the concluded event and its winner, or the halt and the failure behind it — the concluded and halted endings visibly distinct, with a halted event presented as indeterminate (`tournaments/tournament-view#the-wait-is-explained`, `#the-endings-are-distinguishable`, `tournaments/event-outcome`)
- [ ] 7.3 Compose the view with the lobby regions siblings own rather than replacing them, and confirm the read-only stance holds: the view mutates nothing, and a room a tournament governs offers no start affordance to anyone (`tournaments/tournament-view`, `rooms-and-matchmaking/room-lobby#unaffiliated-viewers-see-everything-touch-nothing`, `rooms-and-matchmaking/game-start-gate#a-scheduled-start-does-not-consult-this-gate`)
- [ ] 7.4 Show the forfeit on the event's own standings and completed-round results in the in-room view: a participant that forfeited a round is labelled a forfeiter of that round, not merely carried at the forfeiter's score, while its running total stays exactly the sum the standings rule defines (`tournaments/forfeit-scoring#forfeit-visible-downstream`, `tournaments/event-outcome#standing-is-the-running-total`, `tournaments/tournament-view`)
- [ ] 7.5 Diff the running scoreboard of a game in play so an unseated participant is presented as a forfeiter of that round rather than omitted from the field or shown as a competitor scoring nothing. The forfeit marking is not a team-level aggregate, so it is joined in from the game record and the observation surface stays the sole authority for the aggregates themselves — the diff lands in the surface `live-game-observation` owns, carrying a `// spec:` citation of this capability's requirement, and that capability restates no forfeit rule (`tournaments/forfeit-scoring#live-scoreboard-names-the-absence`, `live-game-observation/scoreboard-sole-aggregate-authority`, `live-game-observation/ui-honours-the-filter`)
- [ ] 7.6 Diff the replay viewer so a round played out with forfeiters presents them as forfeiters from the replay's first moment and throughout, sourced from the persisted replay and the game record rather than reconstructed from an empty field. The diff lands in the surface `replay-and-audit` owns, citing this capability's requirement (`tournaments/forfeit-scoring#the-replay-shows-the-forfeit`, `replay-and-audit/board-level-replay`, `replay-and-audit/unified-replay-viewer`)
- [ ] 7.7 Diff the finished-game result presentations owned by siblings — the per-hosted-team game-history listing, the player and team profile histories, and each ranked leaderboard entry — so a forfeited game is labelled a forfeit beside its score. The ranking arithmetic is untouched: the game stays in the ranked set at the engine's forfeiter score, which those capabilities already own and which this diff neither restates nor recomputes (`tournaments/forfeit-scoring#forfeit-visible-downstream`, `replay-and-audit/team-game-history`, `accounts-and-profiles/player-profile`, `accounts-and-profiles/team-profile`, `accounts-and-profiles/leaderboard#forfeits-rank-rather-than-vanish`)
- [ ] 7.8 Cover the four surfaces with one shared assertion rather than four independent ones: a single forfeited round is reported as a forfeit by the event's standings, the game's result presentation and the listings that carry it, the live scoreboard while it runs, and its replay — so nobody can satisfy the obligation on three surfaces and quietly miss the fourth (`tournaments/forfeit-scoring`, `#forfeit-visible-downstream`, `#live-scoreboard-names-the-absence`, `#the-replay-shows-the-forfeit`)
