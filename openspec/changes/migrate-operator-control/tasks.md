## 2. The staged-move log — not built here

Moved out. The append-only log, the current-turn effective-move read, the
staging reducer's team-granular selection-blind check, and the
no-legality-evaluation posture all belong to the game's own runtime and are
planned in `mint-game-runtime` §2.3 and §3.1–3.5
(`game-runtime/staged-move-log`, `game-runtime/team-scoped-staging`,
`game-runtime/staging-is-unvalidated`). This capability is a *consumer* of that
contract on exactly two paths — the operator's client staging directly into the
instance (4.4) and the effective-move read the board marker renders (4.3) — and
introduces no staged-move state of its own in Convex, in
`packages/centaur-server-lib/`, or in the reference app
(`game-runtime/staged-move-log#single-home`). The one place that absence has to
be actively asserted rather than merely observed is 5.4.

## 3. Operator coordination state (Convex — `packages/convex-centaur-state`, `packages/convex-host`)

- [ ] 3.1 Selection record schema replacing the `_schemaPlaceholder` stub: one record per snake per active game holding the current holder (or none) plus the snake's manual-mode flag, scoped to the owning team. Reconcile the stub's vocabulary in `packages/convex-centaur-state/src/index.ts` (`SnakeConfigRecord.currentSelectorUserId`, `SelectionState.selectorUserId`) with this delta's holder vocabulary and pick one name. Settle at the same time whether the per-snake bot-parameter override shares this row — `migrate-bot-configuration` §2.3 asks this capability to decide and the stub already splits them (`snake_config` / `bot_params`); either answer is fine, but neither change may sit waiting on the other (`operator-control/exclusive-selection`, seam: `bot-configuration/per-snake-portfolio-record`)
- [ ] 3.2 Selection mutations: at most one holder per snake and at most one snake per operator enforced at the mutation contract in a single transaction, with holderless records counted as belonging to no one; displacement only on the caller's explicit request, otherwise rejected with the holder undisturbed; the caller's previous hold released inside the same transaction and observable as a deselection; no non-member ever named as holder (`operator-control/exclusive-selection`, `operator-control/selection-transfer`)
- [ ] 3.3 Manual-mode mutation: every snake starts each game automatic; entry and exit only by the snake's current holder; exit resumes automated staging and resets nothing else; selection and release both leave the flag untouched (`operator-control/manual-mode#fresh-game-all-automatic`, `#exit-resumes-automation`, `#manual-survives-losing-the-holder`, `operator-control/selection-is-view-only#selection-never-flips-manual`, `#release-changes-nothing-else`)
- [ ] 3.4 Clear every selection record for a game at game end, leaving no live selection state to masquerade as a historical record; hook it into the declared lifecycle finish bracket rather than any local status inference, and test that a game which reached `finished` has no surviving selection row (`operator-control/exclusive-selection#cleared-at-finish`, seam: `game-lifecycle/status-authority#no-backward-motion`, and `replay-and-audit` owns reconstructing selection history afterwards)
- [ ] 3.5 Captain boot mutation: refused for any non-Captain caller however invoked, severs the named operator's session as a network drop would, writes no persistent operator state at all (no lockout, no cleared selection, no flag), and permits immediate reconnection (`operator-control/captain-boot`). Two seams to settle before coding. **Captaincy resolution**: the gate needs the team's current Captain, yet this capability declares no `team-management` dependency at any grain — `migrate-team-management` §6.2 raises the same gap from the other side, so agree one answer for both (`team-management/captain-authority`). **Which connection is severed**: with 4.1's dual connection, Convex can sever only the coordination connection — the game-instance connection is validated once at admission, is not dropped when its token expires, and the instance neither knows nor honours captaincy, so a booted operator retains raw staging capability by construction rather than by oversight (`identity-and-authorization/connect-time-validation#expiry-never-disconnects`, `identity-and-authorization/role-bound-privileges#captaincy-invisible-in-game`, `global-invariants/game-instance-hermeticity#seeded-once-never-refreshed`). Unresolved — settle with the author whether boot is bounded to the team's coordination session (presence, tempo, the active set) or something wider is intended; do not close the gap with a client-cooperative disconnect, which `global-invariants/security-enforced-outside-the-library` would not stand behind
- [ ] 3.6 Team-scoped read surface over selection and manual-mode state, for both team member clients and the team's hosting-server credential — this is the surface `bot-framework` consumes for manual-mode exclusion and attention tiers, so it must be a subscription, not a poll target (`operator-control/exclusive-selection`, `operator-control/manual-mode`)

## 4. Live operator interface (Centaur Server — `apps/centaur-server-reference`)

- [ ] 4.1 Dual-connection live binding: one connection to the game's SpacetimeDB instance for observation and staging, one to Convex for coordination state, each authenticated as the operator themself and neither's lifetime dependent on the other; no server relays, re-stages, or re-attributes any operation; the team's nominated host serves the interface and nothing more (`operator-control/operator-dual-connection`)
- [ ] 4.2 Live route with the availability bracket, driven by the lifecycle status the platform holds and never by a locally inferred one: prominent in the team's navigation from the moment the game is playing so an arriving operator finds it without searching, an explanatory empty state when the team has no playing game, and a terminal view with final outcome and replay path — carrying zero mutating affordances — the moment the game finishes (`operator-control/live-interface-availability`, seam: `game-lifecycle/status-authority`)
- [ ] 4.3 Board surface: compose over the shared board rendering (1.4) rather than drawing a board here, feeding it the connection's filtered observation surface and adding one overlay layer of this capability's own — each owned snake's currently effective staged move, updating live on every team client whatever the staging origin. Leave the decoration slots `decision-transparency` requires — candidate-cell colouring and a worst-case overlay — as further layers over the same rendering, and parameterise them by snake rather than by who holds it, since those decorations are required for snakes nobody holds (`operator-control/board-and-move-interface`, `#marker-follows-any-origin`, `application-shell/one-board-rendering#composition-not-replacement`)
- [ ] 4.4 Four-direction staging affordance for the held snake: reflects the currently effective staged direction, marks immediately lethal directions as discouraged yet leaves them selectable — judged client-side with the shared engine's own move validation rather than a parallel implementation — and stages on every pick with no separate commit act. Give the component no inert or preview-only pick state at all, so a decoration layer cannot add one, and make the indistinguishability of exploring and committing legible to the operator (`operator-control/board-and-move-interface#lethal-discouraged-not-blocked`, `#exploration-is-staging`, `#no-second-direction-selector`, `game-runtime/staging-is-unvalidated`)
- [ ] 4.5 Selection gestures and gating: select an eligible team snake, release explicitly or by selecting another, obtain the operator's explicit confirmation before ever issuing the displacing form of the mutation, and render no direction candidates, staging controls, or per-snake edit affordances for any snake the operator does not currently hold (`operator-control/selection-transfer#confirmation-gates-displacement`, `operator-control/selection-is-view-only#no-affordances-without-holding`)
- [ ] 4.6 Manual-mode control and the cross-runtime ordering guarantee: the toggle reflects the flag and is editable by the holder alone; explicit entry stages nothing and locks whatever move is currently effective; a direction pick makes the snake manual with the transition effective no later than the staged move, so no window exists in which automation overwrites the operator. The interface implements no scheduling or automated staging of its own (`operator-control/manual-mode#staging-enters-manual-without-a-gap`, `#explicit-entry-locks-the-current-move`, `#interface-adds-no-automation`)
- [ ] 4.7 Operator presence and identity: a colour that is a pure function of (game, operator) — identical on every client, across reloads and reconnects, for the game's whole lifetime — used for both the connected-teammates presence display and the selection indication on held snakes, plus a connection-quality indicator measured entirely by the client with no server-held state behind it. Presence is served from the Convex coordination state of 3.6, never from the instance's admission records, which no client connection may read at all (`operator-control/operator-presence-and-identity`, seam: `identity-and-authorization/admission-records-private`). The presence display is the component `turn-pacing`'s pacing header decorates
- [ ] 4.8 Captain boot affordance, invisible to non-Captains, with the booted operator's own interface telling them they were removed and reconnection rejoining exactly as after a network drop (`operator-control/captain-boot#no-sticky-lockout`, `#captain-only`)

## 5. Downstream surface and seam integration

- [ ] 5.1 `turn-pacing` seam and the staging window's closing edge: the declaration path consumes exactly what the staged-move log holds at the declaration instant, boot's active-set and quorum consequences are pacing's to author, and the pacing header decorates this capability's presence display and the Captain-control cluster this capability's boot affordance sits in — agree that component boundary so the boot affordance is not built twice. Then settle the edge itself, which no capability currently states: after the team has declared — by Captain submit, by the automated path, or by clock expiry — the affordance must stop presenting picks as live, since a pick that appends an entry resolution will not consume is exactly the silently-does-nothing control `#exploration-is-staging` promises does not exist. Derive that state from the team's declared state on the instance subscription, never from a local timer, and agree with `mint-game-runtime` whether the instance rejects such a staging or accepts-and-ignores it (`game-runtime/staged-move-log#accepted-until-declaration`, `game-runtime/next-turn-bracket#no-silent-reordering`, `turn-pacing/captain-submit#no-flush-after-the-human-decision`, `global-invariants/client-truthfulness#enablement-derives-from-server-state`, `operator-control/captain-boot`, `operator-control/operator-presence-and-identity`)
- [ ] 5.2 `bot-framework` seam — the automation-never-overwrites-the-operator guarantee, which three capabilities touch and none alone discharges: this capability states the invariant, `turn-pacing/scheduled-submission` implements the sweep that must skip manual snakes, and `bot-framework` owns the player that stages. Confirm which side carries it (client ordering, an authorship check in the player, or both, all of which satisfy the requirement), and note the trap before choosing: the player learns the manual flag from its Convex subscription, so client-ordering alone still leaves a propagation window in which the flag has committed and the player has not seen it. The datum an authorship check would read is the log entry's own writer (`operator-control/manual-mode`, `operator-control/selection-is-view-only`, seams: `turn-pacing/scheduled-submission`, `game-runtime/staged-move-attribution#bot-and-operator-distinguishable`). Confirm too that 3.6's subscription is what the attention tiers read
- [ ] 5.3 `decision-transparency` seam, now settled in spec — implement to it: a pick on this affordance stages the direction *and* sets the transparency layer's examined direction, while the examined direction is otherwise client-local state this capability neither reads nor writes. Wire the affordance so the decoration layer subscribes to picks rather than being able to originate them, and add a test that no code path outside this affordance reaches the staging reducer (`operator-control/board-and-move-interface#no-second-direction-selector`, `#exploration-is-staging`, seam: `decision-transparency/examined-subject#operator-pick-also-examines`)
- [ ] 5.4 `replay-and-audit` seam: selection, deselection, manual-mode toggle, and boot each write their action-log entry in the same transaction as the mutation, and the operator's arrival entry joins the tempo write `turn-pacing` performs on every (re)connect. **Move staging is excluded from the action log** — remove `"StageMove"` from the `CentaurActionType` union in `packages/convex-centaur-state/src/index.ts`, which currently contradicts the single-home model. Settle one design constraint this places on 4.1: the departure entry is written by Convex itself as it observes the operator's coordination connection ending, so that connection must be one whose end Convex observes promptly and reliably — a per-call request pattern would leave the log unable to record a drop at all (`game-runtime/staged-move-log#single-home`, `operator-control/exclusive-selection`, `operator-control/captain-boot`, `operator-control/operator-dual-connection`, seam: `replay-and-audit/actors-write-own-entries#the-one-entry-its-actor-cannot-write`)
- [ ] 5.5 Build the interface as a mountable surface, not a screen: three downstream capabilities re-render it with every mutating affordance withheld — `live-game-observation/coach-mode-interface`, `replay-and-audit/team-perspective-replay#live-ui-read-only`, and the replay's rendering of historical selection shadows in each operator's live colour. Take mode and affordances as mounting parameters and state from the binding, per 1.4, so those re-mountings are configurations of this surface rather than second implementations; add no read-only branch of this capability's own, and do not build any of the three (`operator-control/board-and-move-interface`, `operator-control/operator-presence-and-identity#same-colour-on-every-client`, seam: `application-shell/surface-mounting-contract#one-surface-every-mode`)
