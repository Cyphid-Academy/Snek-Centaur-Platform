## 2. Team record and roster storage (Convex component: `packages/convex-snek-platform`)

- [ ] 2.1 Define `centaur_teams` in `schema.ts`: name, display colour, a single structural captain reference, the coach id collection, the archived flag, and the server-nomination anchor with its recorded health fields — the nomination/health *fields* are reserved here with no write or check behaviour, which is `team-server-management`'s, and their shapes are agreed with `migrate-team-server-management` (its task 4.2 is the other half) rather than settled by either side alone. Choose the captaincy representation so a second or absent captain is unrepresentable rather than guarded (`team-management/team-record#exactly-one-captain`, `#captaincy-not-a-member-role`)
- [ ] 2.2 Define the team-membership table associating each human with their team, with by-team / by-user / by-team-and-user indexes and **no** role column of any kind. Current membership only: removal deletes the row, and there is deliberately no membership-history table, no join/leave timestamps, and no soft-delete flag — historical membership is derived from the participating-team snapshots `game-lifecycle/roster-snapshot` keeps, and the limitation this accepts is recorded in this change's design (`team-management/roster-of-operators#members-are-peers`, `#the-roster-is-not-a-history`)
- [ ] 2.3 Reconcile the existing placeholder types with the delta: `packages/convex-snek-platform/src/index.ts`'s `CentaurTeamRecord` has no display colour, no coach collection and no archived flag, has no membership-record type at all, and `schema.ts`'s table comment omits the membership table — make the exported record types the one shape every sibling binds to (`team-management/team-record`, `team-management/roster-of-operators`)
- [ ] 2.4 Read surface exported for consumers: team by id, roster by team, teams by user, coach set, and an archived predicate — consumed by `accounts-and-profiles` (teams browser, team profile), `rooms-and-matchmaking` (enrolment), `bot-configuration` and `operator-control` (captain resolution) (`team-management/team-record`, `team-management/roster-of-operators`, `team-management/coaches#coaches-visible-to-members`)

## 3. Captain-gated team mutations (Convex component + `packages/convex-host` auth wrappers)

- [ ] 3.1 Team creation: one commit writing the team record together with its first membership row, the creating user captain and sole member from the instant the team exists, with no precondition beyond being authenticated — no membership, tenure, standing or platform role. The same call optionally names a captain other than the caller plus initial members and coaches, all in that one commit, so an external roster system founds a complete team without follow-up calls and no observer sees a partial one; do not build the naked-create-then-populate variant (`team-management/team-creation#creator-captains-from-the-first-instant`, `#a-provisioned-team-is-complete-at-once`, `#no-special-standing-required`)
- [ ] 3.2 One captain-gate helper applied to every team mutation, deciding from the authenticated identity at the function contract with no surface-specific variant; take the authenticated-identity plumbing from `identity-and-authorization/mutation-authorization` rather than re-deriving it. Build the gate as an export of this capability, not a private helper: `team-server-management`'s nomination mutation and `bot-configuration`'s team-configuration wrappers gate on this same captaincy and plan to consume it rather than re-implement it — and `bot-configuration` reaches it from a host wrapper, its own records sitting in a different Convex component, so the export must be callable from outside this one (`team-management/captain-authority#non-captain-rejected-at-the-function`)
- [ ] 3.3 Team identity edits (name, display colour): captain-only, and deliberately *not* freeze-gated (`team-management/captain-authority`, `team-management/roster-freeze#identity-edits-stay-open`)
- [ ] 3.4 Membership add/remove: set semantics decided inside the write's own transaction so two racing additions of the same human leave exactly one membership, and removal of the current captain rejected unless captaincy was transferred first (`team-management/roster-of-operators#membership-is-a-set`, `#captain-cannot-leave-uncrowned`)
- [ ] 3.5 Captaincy transfer: target must be a current member (an outsider or a coach who is not a member is rejected), the write touches only the team record's captain reference, and every captain authority moves at once with the former captain left an ordinary member (`team-management/captain-authority#transfer-only-to-a-member`, `#transfer-is-immediate-and-complete`, `team-management/team-record#captaincy-not-a-member-role`)
- [ ] 3.6 Coach designate/undesignate on the team record: no membership row created, no operator standing, no mutation rights conferred, and the current coach set readable by every member. A coach's *privileges* over live game state are `live-game-observation` and `identity-and-authorization/coach-tokens` — not authored or enforced here (`team-management/coaches#coach-gains-no-roster-standing`, `#coaches-visible-to-members`)
- [ ] 3.7 Archive and unarchive as the only retirement: no team-delete function on any surface, archive rejected while the roster is frozen, unarchive by the captain and — as the expressly granted administrative power resolved in this change's Open Question — by a platform admin whose standing comes from `identity-and-authorization/platform-admin-role` rather than a local admin check, with roster, captaincy and coaches restored exactly as they were (`team-management/archive-not-delete#archive-is-the-only-retirement`, `#archive-blocked-while-frozen`, `#admin-unarchive-recovers-abandoned-teams`, `#unarchive-resumes-intact`). Pin the state the gate exists to prevent, not just the gate: a test asserting no archived team is ever an active participant of a game being played, written so that narrowing the freeze predicate of 4.1 fails it (`team-management/archive-not-delete#archived-and-playing-is-unreachable`)
- [ ] 3.8 The archival's room-side effect, authored by the sibling and triggered from this mutation: archiving a team withdraws it from the enrolled set of every room it is enrolled in, committed inside this same transaction so no observable state has the team archived and still enrolled (`rooms-and-matchmaking/team-enrolment#archiving-withdraws-the-team-from-every-room`). The enrolled set is not this capability's record to write — agree the call shape with `migrate-rooms-and-matchmaking` (that capability exposing a withdrawal this mutation invokes, or this mutation routing through its enrolment path), and note how the rules compose: the freeze of 3.7 means an *engaged* team can never reach this path at all, so the withdrawal only ever runs for a team that was merely lined up — and because a team can only be enrolled while its room is configuring (`rooms-and-matchmaking/room-mode`), the withdrawal normally lands on rooms that are between games. The one case where it lands on a room with a game under way is an override-seated launch that left an enrolled team unseated, which that capability admits explicitly (`rooms-and-matchmaking/room-mode#the-withdrawal-is-the-one-change-a-playing-room-admits`) — so this mutation must not assume the target rooms are idle. Unarchive deliberately does **not** restore the withdrawn enrolments — the room's administrative actor re-enrols (`#unarchive-resumes-intact` covers roster, captaincy and coaches, not room enrolment)
- [ ] 3.9 Archived teams hidden from default listings while every historical reference still resolves the team's historical identity, with no per-store cleanup step anywhere — the enrolment bar itself is `rooms-and-matchmaking/team-enrolment` and historical attribution resolves through the participating-team snapshots `game-lifecycle` owns (`team-management/archive-not-delete#history-resolves-after-archive`)

## 4. Roster freeze (Convex component)

- [ ] 4.1 Freeze predicate: a team is frozen at minimum while it is competitively engaged, read from the fact `game-lifecycle/competitive-engagement` publishes — never from game records this capability inspects itself, and never from a second notion of "being played" maintained here. **This seam is not lint-checked**: the spec cannot declare `game-lifecycle` without closing a dependency cycle (see this change's design and Open Question 3), which is why the edge was inverted; the coupling exists in code and in this task. Compose the predicate so additional freeze sources can only lengthen the interval, never shorten it, and so the tournament-wide extension `tournaments` owns plugs in without this capability naming or importing tournaments (`team-management/roster-freeze`)
- [ ] 4.2 Apply the freeze to exactly the competitive-composition mutations — member add, member remove, captaincy transfer, and the server-nomination field — leaving identity edits open. Export the guard for `team-server-management`, whose nomination mutation is frozen by this rule but is that capability's function to write, so the rule is implemented once (`team-management/roster-freeze`)
- [ ] 4.3 Hard rejection with an error naming the freeze — never queued, deferred, or applied once the freeze lifts — with the check evaluated inside the mutation's own transaction so a mutation racing the freeze either completes wholly before it or is rejected (`team-management/roster-freeze#hard-rejection-never-deferral`, `#check-and-write-atomic`)

## 5. Team Management view (`apps/centaur-server-reference`)

- [ ] 5.1 Route and data loading for a team's management view, reachable by every current member from whichever Server deployment they open through their own identity and Convex connection, never through deployment-held privilege. Prerequisite seam: the app has no Convex client and no authenticated session today — sign-in and session are `identity-and-authorization`, and the view is a surface *in* the one application, so it reads through `application-shell/one-state-binding` and is mounted per `application-shell/surface-mounting-contract` rather than hand-rolling a binding of its own (`team-management/team-management-view#every-member-sees-the-whole-picture`)
- [ ] 5.2 Member-visible display: name, display colour, current captain, member roster, designated coaches, and the server nomination with its latest recorded health status — the status value being written by `team-server-management/server-healthcheck`, displayed here (`team-management/team-management-view`, `team-management/coaches#coaches-visible-to-members`)
- [ ] 5.3 Captain-only mutating affordances (identity, membership, coaches, nomination, captaincy transfer) offered to no other member, as presentation over the server-side gate — withholding an affordance is never what enforces the rule. The affordance set is stated by the mounting rather than resolved inside the surface, and its enablement derives from the server-held captain reference, so a captaincy transfer flips it with no reload. `bot-configuration/captain-only-team-configuration#captaincy-change-applies-without-reload` pins that behaviour for *its* configuration surfaces only and does not cover this view — same mechanism, separate obligation (`team-management/captain-authority#captain-only-affordances`, `application-shell/surface-mounting-contract#the-host-states-what-is-offered`, `global-invariants/client-truthfulness#enablement-derives-from-server-state`)
- [ ] 5.4 While the roster is frozen, render the affordances the freeze rejects visibly disabled with an explanation that a game in progress makes them temporarily unavailable, derived from server-held freeze state rather than a client guess, with identity edits left enabled (`team-management/roster-freeze#frozen-affordances-visibly-disabled`, `#identity-edits-stay-open`)
- [ ] 5.5 Enforce the view's scope limit: no bot parameter, heuristic, drive, or any other play-configuration affordance appears — only navigation links out to the team-internal surfaces `bot-configuration` owns (`team-management/team-management-view#management-is-not-play-configuration`)
