## 3. Centaur-subsystem pacing records (Convex — `packages/convex-centaur-state/`, `packages/convex-host/`)

- [ ] 3.1 Add the per-game, per-team live pacing-parameter record holding the three submission-timing values (automatic submission time allocation, scheduled-submission interval, imminent-deadline threshold), with a mid-game retune mutation open to **any** current member of the owning team — the same grain and the same `packages/convex-host/` gate as the game-scoped temperature adjustment, the captain gate governing durability rather than breadth (`bot-configuration/any-member-live-editing#game-scoped-parameters-need-no-captain`) — that leaves team defaults untouched, and make it the single record every consumer reads directly — no consumer reconstructs current values by scanning recorded activity. Initialisation must supply the automatic submission time allocation's default where the team captured none: exactly the clock time the game accrues to the team each turn, read from the game's own timer configuration rather than any platform constant, with a test at a second budget configuration proving the default tracks the format instead of a hard-coded number. The interval and threshold get no spec'd default — an unset one falls back to the plastic code constant (§6.1), never to a placeholder stored back on the record (turn-pacing/live-pacing-parameters, turn-pacing/live-pacing-parameters#live-record-not-derivation, turn-pacing/live-pacing-parameters#mid-game-retuning-is-live, turn-pacing/live-pacing-parameters#unset-allocation-defaults-to-the-turns-accrual, game-engine/chess-timer#carve-out-arithmetic)
- [ ] 3.2 **Shared-record seam to settle with `bot-configuration`:** the same per-game record also carries that capability's captured temperature, and its creation-from-defaults at game start is `bot-configuration/game-start-snapshot`'s act. Agree who defines the table/document and its validator (today `packages/convex-centaur-state/schema.ts` lists `bot_params` and no game-scoped record), and land the timing fields' semantics here without duplicating the capture logic. The captured value must be able to arrive **unset** — `bot-configuration/team-bot-parameters#unset-timing-parameter-stays-unset` stores no placeholder — so the validator and the capture path both carry absence through to this record's initialisation, which is where the default is applied (turn-pacing/live-pacing-parameters#unset-allocation-defaults-to-the-turns-accrual, bot-configuration/game-start-snapshot)
- [ ] 3.3 Publish the live record on the team's Convex subscription so the automated player reads the allocation for two distinct purposes and reads the *same* value for both: arming its final flush (§4.3) and declaring the turn's duration in every simulated resolution (`bot-framework/simulated-turn-timings`). The two consumers take a retune on different beats and this is deliberate: test that a mid-turn retune moves the deadline arming from its next scheduling decision within the same turn, while the simulations keep the value frozen at that turn's start and take the new one only from the next turn — so one turn's stateMap is never a mixture of two projections. Do not "fix" the resulting within-turn divergence by holding the deadline back (turn-pacing/live-pacing-parameters#live-record-not-derivation, turn-pacing/live-pacing-parameters#mid-game-retuning-is-live, bot-framework/simulated-turn-timings#the-turn-holds-one-allocation)
- [ ] 3.4 Add the durable per-game per-operator tempo record and its self-write mutation: written only by the operator it describes, toggleable either way at any moment, never touched by turn boundaries, coaches and admins rejected outright (they hold no tempo), and a write restating the operator's current value accepted as a deliberate act rather than rejected as redundant (turn-pacing/operator-tempo, turn-pacing/operator-tempo#durable-across-turns, turn-pacing/operator-tempo#restating-tempo-is-still-an-act)
- [ ] 3.5 Make flow-on-(re)connect the sole automatic tempo write, applied uniformly on first join, post-drop reconnect, and post-boot rejoin, as part of the session (re)connect sequence — **seam:** the boot act that produces the post-boot path is `operator-control/captain-boot`'s (turn-pacing/operator-tempo#flow-on-every-rejoin, turn-pacing/flow-quorum#boot-leaves-rejoin-restores)
- [ ] 3.6 Implement the active-operator set and the unanimous-flow computation over it — currently connected member operators only, observers never counting either way, zero active operators leaving the precondition unsatisfied. It is computed outside the game instance, which holds no notion of an individual operator (`global-invariants/team-granularity-authorization`); wherever the fold itself lands, the automated player must **read** the result on its own schedule and never be woken by it — `#passive-never-a-trigger` forbids the reactive implementation a subscription invites, so the declaration path re-checks the quorum on its own cadence (§4.4) instead of firing on the transition to unanimity. It gates nothing but that path, leaving every operator interaction available in either tempo and the clock running regardless. **Seam:** action-log entries for tempo and boot events belong to `replay-and-audit/team-action-log` (turn-pacing/flow-quorum, turn-pacing/flow-quorum#observers-never-count, turn-pacing/flow-quorum#zero-operators-defers, turn-pacing/operator-tempo#thinking-stops-only-the-automated-declaration)

## 4. Automated player submission pacing (`packages/centaur-server-lib/`)

- [ ] 4.1 Implement the scheduled submission pass on the team's live scheduled-submission interval, sweeping only automatic-mode snakes whose decision state has news: sample, stage, and re-arm the interval when the live parameter changes. **Seams:** the dirty flag's meaning is `bot-framework/score-composition`'s, sampling is `bot-framework/softmax-decision`'s, the staging write is `game-runtime/staged-move-log`'s, and manual-mode exclusion is `operator-control/manual-mode`'s (turn-pacing/scheduled-submission, turn-pacing/scheduled-submission#no-news-no-reroll)
- [ ] 4.2 Bind the clear of a snake's news to the staging acknowledgement — never at sampling, never at send, and never as a side effect of the decision-state publication the same pass performs — so a failed or unacknowledged staging leaves the snake pending and the next pass retries; test the lost-acknowledgement path and the published-but-not-staged path explicitly. **The clear belongs to the act of staging, not to this pass:** `bot-framework/score-composition` gives it to "the workflow that stages the snake's decided move", and the deadline flush (§4.4) is a second such workflow — route both through one ack-gated staging path, or a flushed snake keeps its news and the cadence that keeps running until declaration re-rolls it straight after the flush. **Seam:** setting the flag (and that publication never consumes it) is `bot-framework/score-composition`'s half of the same lifecycle (turn-pacing/scheduled-submission#ack-gates-the-clear, turn-pacing/scheduled-submission#publishing-is-not-staging)
- [ ] 4.3 Arm the per-turn final-submission deadline from live state — the smaller of the automatic allocation and the observed remaining time, brought forward by the imminent threshold — and re-arm it earlier whenever observed remaining time falls below what the armed deadline assumed, with a test driving a mid-turn shrink (turn-pacing/final-flush, turn-pacing/final-flush#deadline-tracks-the-clock, turn-pacing/final-flush#expiry-never-wastes-decisions)
- [ ] 4.4 Implement the deadline behaviour: flush every automatic-mode snake with pending news however recently staged, then declare the turn over when the flow quorum permits — immediately if it holds at the deadline, otherwise on the player's own schedule later in the turn — while the scheduled cadence keeps running until the turn is actually declared over; the withheld-quorum case flushes but defers declaration (turn-pacing/final-flush#quorum-withheld-flushes-but-defers, turn-pacing/flow-quorum#passive-never-a-trigger)
- [ ] 4.5 Make declaration coordination observation-only: the player learns of *any* declaration — the Captain's submit included — solely from the declared state on its own game subscription, cancels its pending flush from that observation, and exposes no interface-to-player channel. **Seam:** the subscription is the player's own team connection to the game instance, not an operator client's view — `bot-framework/observe-and-stage-only` already has it taking turn number, clock state, and staged moves from that connection, and the declared state rides the same one; the boundary forbidding any other channel is `global-invariants/centaur-state-boundary#bot-to-game-flow-never-routes-through-convex` (turn-pacing/captain-submit#declaration-observed-never-signalled, turn-pacing/captain-submit#no-flush-after-the-human-decision)

## 5. Captain controls and the pacing header (`apps/centaur-server-reference/`)

- [ ] 5.1 Implement the Captain's immediate turn-submit — declaring the team's turn over at once with exactly the moves currently staged, tempo-blind, offered to the current Captain alone, additionally bound to a keyboard shortcut usable without pointer input. Write **no** server-side non-Captain gate on the submission path: the Captain-only allocation is this application's presentation choice, not an access control, and a fork that offers the affordance more widely is behaving correctly. Note the asymmetry with the boot affordance rendered alongside it: `operator-control/captain-boot#captain-only` **is** a server-enforced Convex gate that rejects a non-Captain caller by any means, and this control deliberately is not — two Captain controls in one header with opposite enforcement stories, so do not gate them together. Boot's behaviour is `operator-control/captain-boot`'s; this change mirrors only its header placement (turn-pacing/captain-submit, turn-pacing/captain-submit#immediate-and-tempo-blind, turn-pacing/captain-submit#keyboard-under-pressure, turn-pacing/captain-submit#captain-only-is-allocation-not-enforcement)
- [ ] 5.2 Build the pacing header: current turn number, the team's clock countdown at sub-second precision with a distinct warning state as expiry nears, remaining budget, and each active operator's tempo on the presence display — reading tempo from the durable record and never inferring it from presence, which proves connectedness only. **Seams:** the presence display, operator colour, and the client-measured latency indicator are `operator-control/operator-presence-and-identity`'s (turn-pacing/pacing-header, turn-pacing/pacing-header#sub-second-countdown-with-warning, turn-pacing/pacing-header#tempo-from-the-record)
- [ ] 5.3 Replace the countdown with a stable turn-submitted indicator once the team has declared, holding steady while the remaining teams finish declaring and never flickering back to a countdown before the next turn opens — including across authoritative-update gaps if the countdown interpolates locally between them (turn-pacing/pacing-header#submitted-indicator-holds)
- [ ] 5.4 Expose the operator's own tempo toggle in the header — every member operator's own control, never the Captain's to set on their behalf, durable across turns in the display as in the record, and available in either tempo without affecting any other interaction (turn-pacing/operator-tempo, turn-pacing/operator-tempo#durable-across-turns)
