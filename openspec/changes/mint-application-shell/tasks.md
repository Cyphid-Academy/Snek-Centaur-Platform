- [ ] 1.2 Seam gate — capabilities that must be implemented or agreed first, and which archive before this change: `game-engine` (the domain values the board rendering consumes) and `global-invariants` (the truthfulness and confinement rules the binding rests on). One caveat the graph does not carry: `revise-game-engine-contract` is reshaping `game-engine/domain-vocabulary` — a snake's own turn, and the partial-versus-complete game-state distinction — and by its own design record it folds *after* this change, so the domain values §5 renders are not final. Build the rendering against the revised shape, or budget the rework
- [ ] 1.3 Confirm the runtime home this plan assumes: every requirement here is realised in the one web application the servers serve, with no Convex, SpacetimeDB or hosting-server code in scope — where the application is served from is `centaur-server-runtime`'s, and what any surface *shows* is the story capability's. Concretely, none of these is built here and each mounts into what is: the home view and profiles (`accounts-and-profiles`), a room's lobby (`rooms-and-matchmaking`), the live board-and-move interface (`operator-control`), coach mode (`live-game-observation`), the replay viewer (`replay-and-audit`), the configuration surface (`game-configuration`)
- [ ] 1.4 Settle the package home before writing code, because the fork constrains it: the application is `apps/centaur-server-reference/`, mirrored out by `git subtree split --prefix=apps/centaur-server-reference`, and a fork must build from published artifacts alone (`centaur-server-runtime/published-library-surface#a-fork-builds-without-the-monorepo`). Everything shared this change builds therefore lives either inside that directory or in a package the mirror publishes and rewrites — today `@cyphid/snek-centaur-server-lib` is the only such dependency. A new workspace-only package is the silent way to break every fork

## 2. The application

- [ ] 2.1 Stand up the one application: routes for both platform-wide and team-internal concerns in a single build, with no separate platform application anywhere and no surface reachable only from a platform-operated deployment. "One application" is a claim about platform interactions, not about the repository — `apps/visual-tester` is a second application and stays one (`visual-tester/dedicated-app#isolated-from-product-surfaces`) (`application-shell/unified-web-application`, `#no-second-application`)
- [ ] 2.2 Build the navigation shell — the routing structure, the authenticated frame, the team and game context resolution — as **mechanism**, and record its conventions in the app's `AGENTS.md`. No requirement mandates its shape; what is binding is that every surface lives inside this one application, and story capabilities extend this frame with their own routes and entries rather than standing up a second one (`accounts-and-profiles` builds the platform-scoped navigation on top of it). What "authenticated" means is not built here: sign-in, the session and credential custody are `identity-and-authorization`'s (`identity-and-authorization/google-sign-in`, `identity-and-authorization/authentication-required`), and the frame authenticates against the platform, never against the serving server (`centaur-server-runtime/no-operator-state#no-per-server-sign-in`)
- [ ] 2.3 Verify the serving-server independence: the built application reads its platform endpoint from configuration and holds no per-deployment branch, so the same build is what every server serves (`application-shell/unified-web-application#same-data-any-server`)
- [ ] 2.4 **Seam:** the two route families are this change's; their team-scoping rule is not. That a team-internal surface renders only in the context of one operated team, that a server asked for a team it does not operate refuses with an explanatory state rather than rendering against the wrong server, and that a link into another team's team-internal live surface resolves to that team's home are `team-server-management/shared-hosting` (`#unhosted-team-surface-refused`, `#cross-server-links-resolve-the-home`). Build the split in the shape those need; plan none of that behaviour here

## 3. The mounting contract

- [ ] 3.1 Define the mounting contract every surface is written to: mode and per-affordance parameters supplied at mount, and no access to session, actor, or role from inside a surface. Draw the host/surface line first, because the rule binds the surface and not the host that mounts it — a route or layout is exactly where an actor is resolved and the parameters decided, which is what lets admin affordances appear from server-held state without any surface asking who is present (`identity-and-authorization/platform-admin-role#role-effective-without-reload`). Then make that boundary structural rather than remembered, with a guard that a surface module cannot reach the identity context at all; leave the guard's mechanism to the implementation (`application-shell/surface-mounting-contract`, `#the-host-states-what-is-offered`)
- [ ] 3.2 Test one surface mounted three ways — live, read-only, and over a reconstructed past moment — asserting the rendered output differs only in the affordances the host stated and that the surface holds no mode-aware branch (`application-shell/surface-mounting-contract#one-surface-every-mode`)
- [ ] 3.3 Test that a write of a withheld kind reaching the owning runtime anyway is judged by that runtime's own rules, unchanged by how the surface was mounted (`application-shell/surface-mounting-contract#hiding-is-not-enforcing`)

## 4. The state binding

- [ ] 4.1 Build the binding: one interface through which a surface obtains state, with implementations over the live platform deployment, over a game instance's filtered subscription, and over a fixture — mutation present on the first two and **absent from the type** on the third (`application-shell/one-state-binding`, `#absence-not-refusal`). **Seam:** the binding over a persisted replay record is `replay-and-audit/replay-binding-mutation-free`'s, which declares this requirement. Build the shape it plugs into, and a fixture standing in for it; do not build the replay data path
- [ ] 4.2 Test that the same surface renders live state and the same state from a non-live binding with no source-aware branch, using a surface written before the second binding existed (`application-shell/one-state-binding#a-surface-does-not-know-its-source`)
- [ ] 4.3 Surface connection loss and recovery in the binding, and test that a surface cannot present a stale cache as live state because it never holds one (`application-shell/one-state-binding#loss-is-the-bindings-to-report`)

## 5. Board rendering

- [ ] 5.1 Build the one board rendering component over the engine's own domain values — terrain, snakes, items, hazards, fertile tiles — with an overlay slot for surface-specific marks, and no rendering rule reachable except through it (`application-shell/one-board-rendering`, `#composition-not-replacement`, `#a-rendering-rule-is-stated-once`)
- [ ] 5.2 Test one board rendered from three bindings — a live subscription and two non-live ones standing in for a configuration preview and a replay — asserting identical output for identical state. The preview and replay *surfaces* are `game-configuration`'s and `replay-and-audit`'s and adopt this component when they are built; what is tested here is that the component does not care which binding fed it (`application-shell/one-board-rendering#one-board-everywhere`)
- [ ] 5.3 **Seam:** agree with the author whether `apps/visual-tester` adopts this component. The requirement does not bind it (Q-B); adopting it is a plan decision and, if taken, retires the app-local renderer — and forces the rendering into a package both applications can import, which 1.4's fork constraint then governs. The permitted direction is one-way: the tester may consume shared code, but nothing in the platform's applications may depend on the tester (`visual-tester/dedicated-app#isolated-from-product-surfaces`)
