Being the DAG root makes this capability's *citations* free of peers, not its implementation independent of them; expect §5 to land alongside `game-lifecycle`'s instance work rather than ahead of it
- [ ] 1.4 Install **Better Auth in local install mode** — this change is the "first Convex implementation task" that `packages/convex-host/AGENTS.md` defers auth integration to. The component is embedded in this package's Convex directory so the schema can carry linkage records, the issuer registry, and accepted-assertion identifiers; forking the integration repository is explicitly rejected. Watch the storage boundary it lands on: the auth tables belong to the host, while the platform user record they resolve to stays `accounts-and-profiles`' in `packages/convex-snek-platform`, so the host must not acquire a second copy of it (`platform-persistence/component-boundaries#the-host-adds-authority-not-storage`, accounts-and-profiles/user-record)
- [ ] 1.5 Hold the plugin/policy boundary from the first commit, since it is easiest to violate early: a **project-owned Better Auth plugin** carries protocol only — the issuance endpoint, assertion verification against a principal's published material, single-use enforcement, ceiling intersection, and minting the capability claim — while the issuer registry and its ceilings, the capability registry, principal-kind checks, per-client ceilings and attribution stay in ordinary application code in this package. Policy migrating into the plugin buries the rules most needing review inside a dependency's lifecycle

## 2. Identity foundation in Convex (`packages/convex-host`, `packages/convex-snek-platform`)

- [ ] 2.1 Google sign-in through Better Auth as the only human authentication path, producing a session that survives page loads in the script-inaccessible cookie custody permits, with sign-out terminating the session and revoking the client-held session credential; store no password, hash, or shared secret for a human (identity-and-authorization/google-sign-in, `#google-account-specifically`, `#session-survives-reload`, `#sign-out-clears-client-state`, `#no-human-shared-secrets`)
- [ ] 2.2 Linked provider credentials: a linkage record naming the provider and the provider's immutable subject, created with the user record at first sign-in, and the sole lookup by which an authentication resolves to a user — no other field of the user record identifies them to a provider. Take Better Auth's defaults with automatic linking **off**: its Google provider already keys on the subject and already declines to link by matching email, so the requirement is satisfied by configuration rather than by overriding the account model. Enforce one-to-one in both directions as a uniqueness guard inside the mutation's own transaction so two racing first sign-ins cannot both commit, and afford no operation that repoints, replaces, or detaches a linkage (identity-and-authorization/linked-provider-credentials, `#one-provider-account-one-person-forever`, `#the-linkage-is-the-only-lookup`, `#no-auto-linking-by-email`). Seams: the user record itself is owned by `accounts-and-profiles`; the scaffolding's `googleSub` field on the user record is retired in favour of the linkage row, since every other record names the platform's own user id (global-invariants/durable-identity-references)
- [ ] 2.3 Identity resolution: one entry point returning a closed discriminated union over human identity, Centaur Team credential identity, and derived game-participant identity, so no Convex function can meet an identity of undecidable kind; team identity is the platform-assigned id with the nominated server domain held as configuration outside it (identity-and-authorization/identity-kinds, `#server-domain-is-not-identity`, `#participants-are-derived`)
- [ ] 2.4 Authenticated-call wrappers — the enabling primitive every sibling capability builds on: query/mutation/action wrappers that refuse unauthenticated callers on both reads and writes, resolve the caller to their persistent user record, and make that record the anchor for membership, admin, credential-ownership and attribution questions; the only exempt surfaces are sign-in and public non-user-specific views (identity-and-authorization/authentication-required, `#unauthenticated-refused`, `#user-record-anchors-authorization`)
- [ ] 2.5 Mutation-authorization helper: every platform-state mutation decides the caller's right at the function contract from the authenticated identity and rejects when it is absent — exercised by a test that invokes the function directly, bypassing any interface gating (identity-and-authorization/mutation-authorization, `#ui-gating-is-not-enforcement`)
- [ ] 2.6 Platform admin role: a platform-level designation on the user record (never per-team, never per-server) read reactively so a change takes effect without a reload; a read-breadth helper that bypasses membership filters for team browsing, game history and replays; implicit coach standing for every team's live games; and the bound that the role confers no write path into a live game and no platform mutation a requirement does not expressly grant (identity-and-authorization/platform-admin-role, `#admin-reads-across-all-teams`, `#implicit-coach-everywhere`, `#no-write-path-into-live-games`, `#powers-are-expressly-granted`, `#role-effective-without-reload`)

## 3. Credential and token issuance (`packages/convex-host`)

- [ ] 3.1 Signing material held only inside Convex, and **audience binding rather than separated material per credential type** as what contains a compromise: every issued credential names the exact resource it may be used at, and every resource refuses a credential naming another, checking that binding before anything else about the credential — so one signing arrangement behind all of the platform's credentials is safe rather than a concentration of risk, because a leaked credential is inert outside its named resource and dead within minutes. Register this capability's environment variables with the loud startup env-validation step `mint-platform-persistence` stands up rather than adding a second one, and document them in `docs/external-setup.md` (identity-and-authorization/audience-bound-tokens, `#wrong-audience-refused`, `#compromise-contained`, identity-and-authorization/sole-credential-issuer)
- [ ] 3.2 A single issuance module is the only code path that mints sessions, game credentials, and game access tokens; no other runtime or surface can mint, forge, or re-derive one, and a game instance accepts nothing but a Convex-issued token (identity-and-authorization/sole-credential-issuer, `#no-alternative-admission`, `#app-never-self-issues`)
- [ ] 3.3 Publish token verification material at stable well-known addresses sufficient for any instance to validate entirely on its own, with no per-instance secret provisioned or exchanged and no new arrangement negotiated per instance (identity-and-authorization/verification-without-shared-secrets, `#instance-validates-alone`, `#same-material-platform-wide`). Seam: pointing a provisioned instance at the published material is part of `game-lifecycle`'s provisioning step
- [ ] 3.4 Game access token shape and lifetime: signed, naming the specific game, carrying a subject that encodes role plus its identity binding for all four roles (operator, bot, spectator with no team binding, coach with human and team), and an expiry **fifteen minutes** after issuance — the delta's number and the issuing library's own default; the "two-hour" figure surviving in `design.md`'s constraint-mining notes is stale and must not be built to — plus a replacement path that needs no interactive re-authentication for a holder whose session or credential is still valid (identity-and-authorization/game-token-contents, `#token-names-its-game`, identity-and-authorization/token-lifetime-and-refresh, `#refresh-without-reauth`, `#teardown-not-expiry-ends-access`)
- [ ] 3.5 The four issuance endpoints with their eligibility checks: operator tokens only for a human the target game's roster snapshot places on a participating team; bot tokens only against a valid game credential, for that credential's own team and game; spectator tokens for any authenticated human with no team binding ever attached; coach tokens only for a designated coach (or admin) of a participating team, team-bound and non-mutating (identity-and-authorization/participant-token-eligibility, `#operator-outside-roster-refused`, `#bot-token-requires-team-credential`, identity-and-authorization/spectator-tokens, `#any-authenticated-human-may-request`, `#no-team-binding`, identity-and-authorization/coach-tokens, `#coach-reads-as-bound-team`, `#coach-of-nonparticipating-team-refused`). Seams: coach designation is read from `team-management`; what a coach or spectator connection then experiences belongs to `live-game-observation`
- [ ] 3.6 Per-request liveness re-check on every credential-authenticated call and every token issuance, refusing when the game is finished or not yet started regardless of remaining cryptographic validity (identity-and-authorization/live-game-issuance, `#credential-dead-at-finish`, `#no-tokens-for-finished-games`). Seam: game status is owned by `game-lifecycle`
- [ ] 3.7 Per-team game credential enforcement: resolve every credential-authenticated call to the credential's own team and game, refuse any use outside them, and bound the credential to exactly two capabilities — that team's own Centaur-subsystem writes and that team's bot-token requests (identity-and-authorization/game-credential-scope, `#not-valid-for-another-team`, `#not-valid-for-another-game`, `#grants-nothing-beyond-the-two`). Seams: **no capability delivers this credential** — a Server earns each one itself through the assertion exchange of 4.2 once it has accepted a game invitation, and the two independent facts that gate issuance (the captain's homing record, the Server's own request) are `team-server-management/two-sided-consent`'s; the Centaur-state writes it authorizes belong to `bot-configuration` / `operator-control`
- [ ] 3.8 Convex-side snapshot binding: operator-token eligibility and participating team identities are answered from the game's initialization roster snapshot for the game's whole life, never from current team records (identity-and-authorization/roster-snapshot-binding, `#running-game-reads-only-the-snapshot`). Seam: the snapshot's creation and storage belong to `game-lifecycle`; the roster mutation freeze to `team-management`

## 4. Federated trust: issuers, assertions, and the capability model (`packages/convex-host`)

- [ ] 4.1 Trusted-issuer registry: a table of the issuers the platform trusts — its own deployment and zero or more registered external systems — each with an issuer identifier, the location at which it publishes verification material, and its capability ceiling. The registry holds **no secret for any issuer**, and the code reads it as a set from the first line rather than special-casing a single peer, so the second registration is a row and not a refactor (identity-and-authorization/trusted-issuer-registry, `#registry-holds-no-secret`, `#the-set-is-never-assumed-singular`). Seam: the client records themselves are `platform-integrations`' (`integration-clients`) — this owns the trust anchor, not the client lifecycle — and `platform-integrations/client-registration` records the same issuer identifier, publication location and ceiling with label, registrar and revocation on top, so plan one record read as a registry row rather than a second table to keep in step
- [ ] 4.2 Service-principal assertion exchange (the Better Auth plugin of 1.5): accept a short-lived assertion the principal signed with its own key, naming itself, naming this issuance endpoint as the only place it may be used, and carrying an identifier unique to that assertion; verify the signature against the material published at the location recorded for that principal, check the audience, and refuse an unregistered principal. Persist accepted assertion identifiers so a replay is refused, and re-resolve published material rather than pinning a key, so a principal rotates without coordinating with the platform (identity-and-authorization/service-principal-assertions, `#unregistered-principal-refused`, `#replayed-assertion-refused`, `#rotation-needs-no-coordination`). Seam — one exchange, two registration sources, neither of them this change's: a Snek Centaur Server resolves against the captain's homing record plus the key its own domain publishes at the platform-wide well-known path (team-server-management/server-nomination, centaur-server-runtime/server-key-publication), a peer system against its client registration (`platform-integrations/client-registration`). Write the exchange over a registration lookup, never over either shape
- [ ] 4.3 Ceiling intersection at mint time, and its loud failure: a request for capabilities outside the requesting issuer's recorded ceiling is refused rather than silently narrowed, so a misconfigured integration fails visibly instead of appearing to work with less authority than it asked for (identity-and-authorization/trusted-issuer-registry#excess-fails-loudly, global-invariants/issuer-anchored-trust#ceiling-is-checked-at-the-resource)
- [ ] 4.4 Structured capability claim: every issued credential carries its capabilities as a sequence of entries read structurally from the first line of enforcement code, never a string an enforcement site splits. An entry names one capability as a **bare verb identifier and carries nothing else today** — build no constraint machinery before there is a constraint to express; the sequence is what lets one be added later as a change to minting alone. Where a service principal obtained the credential, it also names that principal (identity-and-authorization/capability-claim-structure, `#structured-from-the-first-token`, `#uniform-today-attenuable-tomorrow`, `#acting-principal-is-recorded`)
- [ ] 4.5 Capability registry over the public function surface, **total at build time**: every publicly exposed function declares the capability that reaches it, explicitly rather than derived from its file location, and a public function with no declaration fails the build. This is the change's one piece of build-breaking shared tooling — a check that enumerates public functions and their declarations, with a red test proving an undeclared function actually fails rather than passing vacuously. A capability grants reachability only: the function's own authorization decision runs regardless of how broadly the caller was scoped (identity-and-authorization/capability-registry, `#unregistered-function-fails-the-build`, `#capabilities-are-declared-not-derived`, `#reachability-is-not-authorization`, `#naming-one-function-is-a-contract`)
- [ ] 4.6 Principal-kind gating at the function, ordered after the capability check: every public function declares which kinds of principal it accepts and itself refuses a caller of an undeclared kind however broad that caller's capabilities. Human-only is the default a function departs from explicitly — so most functions are not callable by a service principal, and the documented programmatic surface is exactly the set declaring otherwise. Team administration excludes the Centaur Team principal, and changing authentication configuration is human-only (identity-and-authorization/principal-kind-gating, `#a-service-principal-cannot-administer-a-team`, `#kind-is-checked-independently-of-capability`, `#service-reach-is-declared-never-inferred`). Seam: which functions the surface needs is `platform-integrations/functions-are-the-api`'s
- [ ] 4.7 Bound every external system's ceiling below the user it acts for: no ceiling includes destroying platform state, issuing credentials for a human, or changing authentication configuration, regardless of what such a user could do directly; bound each registered system's call rate; and make the record able to show a user which actions on their behalf were taken through which system (identity-and-authorization/peer-capability-ceiling, `#ceiling-sits-below-the-user`, `#attribution-is-user-visible`). Note the deliberate exclusion: a peer's own token carries no platform authority of its own (identity-and-authorization/sole-credential-issuer#peer-tokens-carry-no-platform-authority)

## 5. Game-instance admission and in-game authorization (`packages/stdb`)

- [ ] 5.1 Validate a connection's token exactly once at connection time and persist the resulting role and team association for the connection's lifetime, so a mid-game expiry never drops an established connection while a reconnecting client is validated afresh (identity-and-authorization/connect-time-validation, `#expiry-never-disconnects`, `#reconnect-revalidates`)
- [ ] 5.2 Admission checks answered entirely from state seeded at initialization — signature, game binding, expiry, and participant-team registration — with rejection disconnecting the client inside the reducer transaction so no admission record, attribution entry, or other trace is written; gameplay mutations accepted only from admitted connections (identity-and-authorization/admission-validation, `#reject-before-touching-state`, `#unregistered-team-refused`, `#unadmitted-mutations-rejected`, identity-and-authorization/roster-snapshot-binding). Seam: seeding that state is `game-lifecycle`'s initialization payload
- [ ] 5.3 Keep the instance's admission and identity-binding records off every client-readable surface — no query, no subscription, no row-level exception — with the platform's end-of-game retrieval the only reader (identity-and-authorization/admission-records-private, `#no-subscription-reaches-admission-records`). Seams: this change owns the rule and the assertion that proves it, while the filtered-view surface where it is honoured is `live-game-observation`'s; the attribution entry itself — the agent value resolved at admission and never mutated — is `game-runtime/connect-time-attribution`'s, written in the same connect reducer the admission decision runs in, and its persisted form is `replay-and-audit/agent-form-persistence`'s. Confirm with `operator-control` and `live-game-observation` that teammate-presence display is served from Convex coordination state rather than these records
- [ ] 5.4 Derive every in-game privilege from the validated role and team binding alone: operator and bot connections mutate only for their bound team, spectator and coach connections are refused by every state-mutating operation, and no platform-side distinction — captaincy, admin standing — reaches inside the instance (identity-and-authorization/role-bound-privileges, `#spectator-and-coach-never-mutate`, `#captaincy-invisible-in-game`). Seam: most of the module belongs to other capabilities — its reducers, staged-move log and turn-keyed record are `game-runtime`'s (whose staging check reads the binding established here), initialization is `game-lifecycle`'s, the filtered views are `live-game-observation`'s; only admission and role gating are implemented here

## 6. Client custody and identity surfaces (`apps/centaur-server-reference`)

- [ ] 6.1 Sign-in and sign-out flow in the web application, with everything beyond sign-in and public non-user-specific views refused to an unauthenticated visitor (identity-and-authorization/google-sign-in, identity-and-authorization/authentication-required, `#unauthenticated-refused`)
- [ ] 6.2 Credential custody in the client: access tokens and game credentials live in component memory for the duration of use — never browser storage, never a URL — a reload re-obtains rather than recovers them, and no surface displays or transmits credential plaintext. The session credential is the single exception, held in the script-inaccessible cookie of 2.1: it is the one thing a reload recovers, and every other credential is obtained afresh under it (identity-and-authorization/client-credential-custody, `#memory-only`, `#the-session-is-the-only-thing-a-reload-recovers`)
- [ ] 6.3 Admin affordances rendered from the authenticated user's server-held designation, appearing and disappearing without a page reload or fresh session (identity-and-authorization/platform-admin-role, `#role-effective-without-reload`)
- [ ] 6.4 Verify the custody mechanism end to end rather than trusting it by construction — the session question is settled (the script-inaccessible cookie), so what remains is proving it: assert from a page context that the session credential is unreadable by script, that it travels only to the platform's own origin over HTTPS, that a reload re-establishes the session with no fresh sign-in, and that sign-out leaves nothing behind that still authenticates. Those four are what make surviving a reload and memory-only custody compatible rather than contradictory (identity-and-authorization/client-credential-custody#the-session-is-the-only-thing-a-reload-recovers, identity-and-authorization/google-sign-in#session-survives-reload, `#sign-out-clears-client-state`)
- [ ] 6.5 Renew ahead of expiry, never in reaction to a refusal: hold each credential behind a timer that replaces it well inside its fifteen minutes, and on a failed renewal retry silently while the credential in hand is still valid, surfacing the loss only when it actually lapses. The natural implementation — refresh on the first refusal — is the one the requirement forbids, because it pays the retry with the chess clock running (identity-and-authorization/token-lifetime-and-refresh#renewal-is-proactive-never-reactive, `#renewal-failure-is-quiet-until-it-bites`). Seam: a Snek Centaur Server holds credentials on the same terms, but its custody and in-process handoff are `team-server-management`'s in `packages/centaur-server-lib` — check at implementation whether the renewal scheduler is shared with it or written twice
