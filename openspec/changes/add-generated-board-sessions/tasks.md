# Implementation plan — add-generated-board-sessions

Scope: one requirement and a Purpose amendment on `visual-tester`, plus the
code work that closes the gap between the requirement and the generation path
the tool already has. Nothing here builds a generator — the point of the
requirement is that the tool never grows one.

## 2. Generation as a second board source in the tool (`apps/visual-tester/`)

The tool's two ways of obtaining a starting board are both first class: hand-authoring, which it has always had, and running the platform's own generator over parameters and a seed, which it has quietly had in code and never in spec. All of it stays inside the browser-side dev app.

- [ ] 2.1 Establish the tester as a conforming *caller* of the one generator — the whole of what this change owns here. `apps/visual-tester/src/lib/factory.ts` already calls the generator the engine package exports and `store.svelte.ts` starts a session on what it returns; keep it to that one call site and no copy. The algorithm's home changes when it is extracted (`revise-game-engine-contract` §12.6) and nothing here should depend on which package hosts it. The guard that no surface reimplements generation, and the test pinning the authoring carve-out, are `mint-platform-persistence` §6.4–6.5's — that plan already assigns this call site to this change rather than claiming it. Note what does **not** follow: the tester runs the generator in its own process, and `game-configuration`'s "generation is platform-side, never a client's" rules are written for a game's preview and its launch — the tester has no game record, and acquiring a platform dependency to satisfy this requirement would cost it the independence it exists for (visual-tester/generated-board-sessions, visual-tester/dedicated-app, global-invariants/one-shared-generation#preview-and-launch-are-one-implementation)
- [ ] 2.2 Let the seed be supplied, not only drawn: the generation path draws a fresh random seed on every invocation today, so the same parameters and seed can never be re-run and the determinism this requirement promises is unobservable from inside the tool — which is the one place a tester would go to check it. Show the seed that produced the board on screen, accept one back, and test that a re-run reproduces the board rather than merely a board of the same shape; reproducibility covers the whole bounded retry ladder, a decline included, not a single attempt. The rule that the game seed reaches no game client bounds a game's clients — the tool already edits the game seed and is not one (visual-tester/generated-board-sessions#same-parameters-and-seed-same-board, visual-tester/board-editor, game-configuration/board-generation-retry#reproducible-retries)
- [ ] 2.3 Follow the generation parameters to their new declaration and present their bounds. The panel does not re-type them today — it reads defaults from the engine's orchestration config and states no range at all, so the values it accepts are unbounded — and that engine-side declaration is exactly what `revise-game-engine-contract` §12.4 removes. `migrate-game-configuration` §7.2 authors the replacement, already names this panel as one of its three consumers, and commits to a home a dev app can import rather than one inside a Convex component; this change consumes it and adds the bounds the panel lacks. Restate no range here — a tester's widget disagreeing with the platform's is the drift this tool exists to catch (visual-tester/generated-board-sessions, game-configuration/generation-parameters, game-configuration/parameter-bounds-sourcing#widget-and-validator-agree)
- [ ] 2.4 Reconcile the teams a generated board is produced for with the teams the session is configured with: the generation path names two default teams of its own, matched to the store's defaults, so the mismatch appears the moment the tester configures a different roster. Decide with the author which side wins — the generator already takes the roster as an argument, so neither answer is expensive — noting the answer is partly fixed already: teams arriving in a generated state without a configuration get a default name and the next colour either way, and platform-side the roster is one of generation's own inputs (visual-tester/generated-board-sessions#generation-is-a-session-source, visual-tester/team-configuration, game-configuration/board-preview#roster-change-regenerates)
- [ ] 2.5 Cover the decline path as a first-class outcome rather than a UI nicety — an infeasible parameter set leaves the current session exactly as it was, names the constraint that failed, and never substitutes a board — since a tool that silently swapped in a board of its own would be reporting on something other than what the tester asked for (visual-tester/generated-board-sessions#declined-generation-changes-nothing, game-configuration/board-generation-retry#infeasible-configuration)

**Deferred, and stated here so the end state is not lost** (not this change's work):

- [ ] 2.6 Aim at the common board-generation component the author recorded as the end state (proposal Open Question 2) — configuration parameters and a seed in, a deterministic board out — that every surface needing a board calls, this tool included. That is the extraction planned as `revise-game-engine-contract` §12.6; the tester follows it as one more caller, which is why the requirement is worded around the shared implementation *however it is packaged* and re-opens no spec. It does not merge this tool's surface into a platform one: the tester keeps its own board rendering and its tester-only overlays, `application-shell/one-board-rendering` binds the application's surfaces rather than this app, and `migrate-game-configuration` §5.7 holds the same line from the other side (visual-tester/generated-board-sessions, global-invariants/one-shared-generation#a-local-preview-is-a-second-implementation)

## 3. Verification

- [ ] 3.1 Test the parity claim directly rather than assuming it: a generated board and a hand-authored one produce sessions that behave identically under staging, simulation, scrubbing, autosave and promotion to a fixture, and a generated board survives being edited into a state generation would never produce — the same edit-and-fixture ground the one-implementation invariant deliberately leaves ungoverned. `revise-game-engine-contract` §11 adds per-turn timings to session history and to what a fixture stores, so write the parity test against that shape rather than today's (visual-tester/generated-board-sessions#generation-is-a-session-source, visual-tester/generated-board-sessions#a-generated-board-is-editable, visual-tester/generated-board-sessions#hand-authoring-needs-no-generator, visual-tester/board-editor#arbitrary-states-allowed, global-invariants/one-shared-generation#authoring-a-board-is-not-generating-one)
