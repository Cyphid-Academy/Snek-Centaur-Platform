## 2. Homing and the play gate (Convex — `packages/convex-snek-platform`, `packages/convex-host`)

- [ ] 2.1 Homing mutation over the team record's home domain — set, change, clear — captain-only and frozen while the team is playing, with the captain-only gate and the freeze consumed from `team-management/captain-authority` and `team-management/roster-freeze` rather than re-implemented. A third, independent gate the captain-only check does not imply: the mutation is barred to the Centaur Team principal by kind, which is what stops a compromised server re-homing the team it operates (seam — that gate is `identity-and-authorization/principal-kind-gating#a-service-principal-cannot-administer-a-team`'s, declared here and enforced there). Naming a domain the captain does not control is harmless and must not be treated as an error (team-server-management/server-nomination, `#naming-is-the-captains-act-alone`, `#naming-a-domain-you-do-not-control-is-harmless`, `#clearing-is-allowed`)
- [ ] 2.2 On naming, read the domain's published verification material over an authenticated transport to confirm it exists and parses, and record the homing record — keeping **two separate facts separately**: that the domain controls its own key, and that the captain associated that domain with this team. Conflating them is what would let one imply the other (team-server-management/server-nomination)
- [ ] 2.3 Two-sided consent as the authorization rule for every server action on a team's behalf: a server acts for a team only where the captain has named its domain **and** the server, proving control of that domain, has asked for that team's credential. Neither fact alone confers anything, and re-homing cuts the old server off — test all three directions (named-but-never-asked, asked-but-never-named, re-homed). This is not a second issuance endpoint: it is the team-scope decision inside the one issuance path `identity-and-authorization/service-principal-assertions` owns, to which this capability contributes the homing predicate (team-server-management/two-sided-consent, `#naming-without-asking-confers-nothing`, `#asking-without-being-named-confers-nothing`, `#re-homing-cuts-the-old-server-off`)
- [ ] 2.4 Play gate in the Convex function contract: a team with no home named is refused entry to a game, and no flow anywhere offers a home-less configuration. Enforced where the platform commits a team to a game, not only in a UI affordance. **Settle this seam before writing it**: every mutation that puts a team forward is a sibling's — `rooms-and-matchmaking/team-enrolment`, `rooms-and-matchmaking/team-readiness`, `rooms-and-matchmaking/game-start-gate`, `game-lifecycle/launch-orchestration` — and no sibling delta declares a dependency on this requirement, so which of them carries the gate is unassigned in the corpus and must be agreed, not assumed. Building a helper here that nobody calls, or editing a sibling's mutation unilaterally, are the two failure modes (team-server-management/nomination-required-to-play, `#empty-nomination-bars-entry`, `#no-pure-human-path`)
- [ ] 2.5 Homing inbox query, scoped to the authenticated server's own domain, returning the teams that have named it. It is informational and confers nothing — a server may read it and whitelist none of them — and it must not leak another domain's inbound teams (team-server-management/homing-inbox, `#inbox-shows-only-your-own`, `#reading-the-inbox-admits-nobody`)
- [ ] 2.6 Hold no representation of a server's own admission decision anywhere in the platform schema, and offer no approval step: which teams a server operates is the server's business, expressed only in its answers to invitations. Carry this as a schema comment plus a test pinning the absence, so adding such a table later is a deliberate, visible act (team-server-management/whitelist-admission)

## 3. Invitation delivery (Convex — `packages/convex-host` action)

- [ ] 3.1 Invitation sender: one POST per participating team — two POSTs when two teams share a home — to the single well-known path fixed platform-wide on each home domain, HTTPS only with plain-HTTP domains receiving nothing, all deliveries issued concurrently, each awaited for a bounded ten-second window after which no answer counts as non-acceptance. The sender lives here and is invoked by `game-lifecycle/launch-orchestration`'s launch sequence — one implementation, called, never a second one written there (team-server-management/game-invitations, `#one-invitation-per-team`, `#https-only`, `#bounded-concurrent-delivery`)
- [ ] 3.2 The invitation is a **bare notification** naming the game and the team, carrying no credential and conferring nothing, with the response's status as the whole answer. This is the section's most important negative: nothing signs it, nothing in it is actable, and forging it buys only a wasted wake-up. Test that the payload carries no credential and that the sender needs no secret-handling discipline (team-server-management/game-invitations#the-invitation-carries-no-authority)
- [ ] 3.3 Wake a sleeping server: the notification must be sufficient to start a scaled-to-zero deployment, which is why it can require no prior subscription and no authentication to receive — a server holding no credential while idle is exactly the case this shape exists for. The consequence for 3.1: the ten seconds is the whole budget with the cold start inside it, so the platform's client timeout *is* the window and never something tighter (team-server-management/game-invitations#wakes-a-sleeping-server)
- [ ] 3.4 Seat a team into a starting game only on its home server's acceptance, as a participation precondition with no branching here — what a decline or timeout *causes* (abort, forfeit, walkover) is `game-lifecycle`'s and is deliberately not planned in this change (team-server-management/invitation-acceptance#acceptance-gates-the-team)

## 4. Availability recording — the platform's half only (Convex — `packages/convex-host` action, `packages/convex-snek-platform` record)

- [ ] 4.1 An on-demand check of a team's home domain that records the resulting status and its timestamp; no polling scheduler, cron, or background sweep is added, and the recorded timestamp is what makes staleness visible. The one-sided call timeout stays in code with a `// design:` reference. The endpoint being called is not built here — it is `centaur-server-runtime/healthcheck-endpoint`, and this section has no server-side half (team-server-management/server-healthcheck, `#on-demand-not-polled`)
- [ ] 4.2 Persist the recorded status and timestamp against the team record — a field addition on the record `team-management/team-record` owns (seam: agree the field shapes with that capability rather than defining them unilaterally) — and display the recorded value on the team's management surface, which `team-management/team-management-view` owns (team-server-management/server-healthcheck)
- [ ] 4.3 Member-triggered check: expose it as one action any surface can invoke on a member's behalf, wired surface-generically so this capability names no downstream room vocabulary. Exactly one consuming surface is pinned by the corpus — the Team Management view, which `team-management/team-management-view` already requires to show the nomination with its latest recorded health. A pre-game affordance is **not** owned anywhere today: `rooms-and-matchmaking/room-lobby` lists no such control, and `rooms-and-matchmaking/team-readiness` is the captain's ready declaration, an unrelated thing that shares the word. Treat a lobby ping as an addition to agree at that seam, never as one already arriving (team-server-management/server-healthcheck#member-triggered-check)

## 5. The server's half: answering, authenticating, holding the credential (`packages/centaur-server-lib`, `apps/centaur-server-reference`)

- [ ] 5.1 Outward authentication in the library: on accepting an invitation, sign a short-lived assertion with the server's own key and exchange it at the platform's issuance endpoint for the team's credential — the same flow every principal uses, per `identity-and-authorization/service-principal-assertions` (seam: the endpoint, verification, single-use enforcement and ceiling intersection are that capability's). The key it signs with is not generated, persisted, or published here either — that is `centaur-server-runtime/server-key-publication`, and this task consumes it. Nothing about the invitation is trusted or verified; authority comes from homing plus proof of domain control (team-server-management/two-sided-consent, team-server-management/invitation-acceptance#accepting-then-authenticating)
- [ ] 5.2 An unattended team still plays: the accept-then-authenticate path requires no operator present and no human session anywhere in it. Test that a server with nobody signed in accepts, authenticates, and operates (team-server-management/invitation-acceptance#nobody-has-to-be-watching)
- [ ] 5.3 Acceptance policy in the reference implementation, replacing the current stub: decide from a whitelist of admitted teams, declining any team absent from it, and treat whitelisting and being named as independent and order-independent — either order is valid and neither is an error. A Cyphid-operated Reference Centaur Server does not auto-admit. What is built here is the *decision that reads* the whitelist; the whitelist's store and the administration API that populates it are `centaur-server-runtime/server-administration-api`'s (team-server-management/invitation-acceptance#whitelist-refusal, team-server-management/whitelist-admission, `#either-order-works`, `#unwhitelisted-team-simply-waits`, `#the-reference-server-does-not-auto-admit`)
- [ ] 5.4 Credential custody on acceptance: the credential the server earned passes in-process to the team's hosting session and lives in memory for the game's duration only — never durable storage, never any outward interface — while the server's **own signing key is the one thing it persists**. Booting and running the hosting session is `bot-framework/embedded-team-player`'s (seam — this change plans the handoff, not the session) (identity-and-authorization/client-credential-custody#own-key-is-the-only-thing-at-rest)

## 6. Shared hosting over time, and the reference home

- [ ] 6.1 Shared hosting in one server process: several teams operated simultaneously (opponents in one game included, on the Server trust boundary's terms), a team switching homes between games with no re-registration and its prior history intact, and exactly one server per team per game. Split the route families the delta requires — team-internal surfaces rendered only in the context of one operated team and refused with an explanatory state otherwise, platform-wide surfaces team-independent and identical on every server, and links into another team's team-internal live surface resolved to that team's own **home**. That route split is a *coherence* contract, not a security boundary, and it is all this section builds of multi-tenancy: keeping co-tenants' credentials and compute apart is `centaur-server-runtime/library-tenant-separation`'s, and the operator-trust terms are `global-invariants/server-trust-boundary`'s (team-server-management/shared-hosting, `#one-server-per-team-per-game`, `#switching-between-games`, `#unhosted-team-surface-refused`, `#cross-server-links-resolve-the-home`)
- [ ] 6.2 Operate a Cyphid Reference Centaur Server as a home for teams running no infrastructure of their own — a deployment and an admission process rather than code, the acceptance policy it runs being task 5.3's — holding no platform privilege another server lacks; record its concentration of teams as the operational consequence it is, protected by its domain and transport posture rather than by any special standing (team-server-management/reference-server-home, `#a-team-with-no-infrastructure-can-play`, `#the-reference-server-is-just-a-server`)
