## 2. Centaur-state schema (Convex Component, `packages/convex-centaur-state/`)

- [ ] 2.1 Team-scoped tables: one row per heuristic identifier per team carrying type, default weight, active-by-default flag (Preferences) and display nickname (Drives); plus the per-team bot parameter record holding the default temperature, the three submission-timing scalars, and the ordered pinned-heuristics list — each of the three timing scalars **nullable**, so a team that never set one is stored and captured as unset rather than carrying a placeholder (`bot-configuration/team-heuristic-defaults`, `bot-configuration/team-bot-parameters`, `#pinning-is-team-configuration`, `#timing-parameters-are-tunable-not-constants`, `#unset-timing-parameter-stays-unset`). The timing scalars are stored and snapshotted only — no consumption semantics here, and no default value either: what an unset allocation means is `turn-pacing/live-pacing-parameters#unset-allocation-defaults-to-the-turns-accrual`'s, applied when the game's live record is initialised
- [ ] 2.2 Game-scoped tables: the per-game captured team defaults and the per-game-per-team forked parameter record the snapshot writes (`bot-configuration/game-start-snapshot`). Seam: `turn-pacing/live-pacing-parameters` owns that record's timing semantics and its live-adjust path — this change owns its creation from the captured defaults, its temperature field, and the authority grain both adjust paths share (`bot-configuration/any-member-live-editing#game-scoped-parameters-need-no-captain`)
- [ ] 2.3 Portfolio tables: per-snake active Drives each carrying a concrete target (target kind + target identity) and current weight; per-snake weight/activation overrides; and the nullable per-snake temperature override (`bot-configuration/per-snake-portfolio-record`, `#no-drive-without-a-target`, `#temperature-override-survives-deselection`). Resolve with `operator-control` where the temperature override physically sits: the legacy mechanism co-locates it with selection and manual mode on one per-snake row that `operator-control/exclusive-selection` and `operator-control/manual-mode` own — either split it into a portfolio-owned row or agree a shared row with per-field ownership
- [ ] 2.4 Reconcile the existing placeholder vocabulary against this delta: `HeuristicConfigRecord` carries a `snakeId` (the defaults are team-scoped, not per-snake), `BotParamsRecord` is keyed by game+snake and holds only a temperature (the record is team-scoped and holds five fields plus the pinned list), `DriveRecord` has no target kind, and no type carries activation, nickname, or pinning. Reshape the exported types, `schema.ts`, and `packages/convex-centaur-state/AGENTS.md`'s table list accordingly
- [ ] 2.5 Team-lifetime retention: no team lifecycle event — server replacement, archive, unarchive — deletes, resets, or re-seeds team-scoped configuration, with tests over the archive/unarchive round trip (`bot-configuration/team-heuristic-defaults#server-replacement-inherits-defaults`, `#archiving-preserves-configuration`). Depends on `team-management/archive-not-delete` for the archive semantics themselves

## 3. Team-scoped configuration contract (component functions + `packages/convex-host/` wrappers)

- [ ] 3.1 Component mutations and queries for team-scoped configuration: create/update/delete a heuristic default entry, edit the bot parameter record, set and reorder the pinned list, read the defaults and the parameter record (`bot-configuration/team-heuristic-defaults`, `bot-configuration/team-bot-parameters`). Seed the interval and threshold scalars' initial values in code with a `// design:` reference to this change rather than in the spec; leave the automatic submission time allocation unset unless a captain sets it, with a test that an edit clearing a timing parameter stores absence rather than a zero or a re-seeded constant (`bot-configuration/team-bot-parameters#unset-timing-parameter-stays-unset`)
- [ ] 3.2 The registry-sync mutation: takes a serialisable projection of the hosting build's registered heuristics and inserts a row at the registry's declared defaults for each identifier with no row, returning the newly inserted identifiers. Insert-only — an existing row is never patched, whatever the registry now declares (`bot-configuration/registry-sync-insert-only`, `#sync-never-overwrites`)
- [ ] 3.3 Host-layer authorization wrappers in `packages/convex-host/`: every team-scoped configuration mutation gated on the caller being the team's current captain, and every read granted to current members and to the team's coaches unconditionally in game state. The gate must live in the host wrapper, not in the component, because the component's table isolation puts the team record and roster in `packages/convex-snek-platform/` where only the host can join them; the component's functions are reachable only through the host, which is what keeps the gate the single contract (`bot-configuration/captain-only-team-configuration`, `#non-captain-write-rejected-at-the-function`, `#members-and-coaches-read-regardless-of-game-state`). Enforcement mechanics are `identity-and-authorization/mutation-authorization`'s; the captain identity and coach set are `team-management`'s
- [ ] 3.4 Bar the framework from configuration writes: the typed Convex client `packages/centaur-server-lib/` hands the framework exposes configuration reads only, and the host rejects a team-scoped configuration mutation presented under a game credential rather than an operator identity, with a test per mutation (`bot-configuration/registry-sync-insert-only#framework-never-writes-configuration`, cites `global-invariants/one-contract-many-surfaces`)
- [ ] 3.5 Reactive captaincy: the configuration surfaces' captain-gated affordances derive enablement from the server-held captaincy subscription so a transfer flips them on both clients with no reload (`bot-configuration/captain-only-team-configuration#captaincy-change-applies-without-reload`, cites `global-invariants/client-truthfulness`)

## 4. Game-start snapshot and the availability intersection

- [ ] 4.1 The game-start initialization mutation in the component: read the team's defaults and parameters at that moment, create each team snake's portfolio holding exactly the active-by-default Preferences at their default weights with no Drives and no overrides, and fork the parameter record into game-scoped values; idempotent on re-invocation, and keyed by exactly the snake identifiers the launch delivers (`bot-configuration/game-start-snapshot`, `#initial-portfolio-is-defaults-only`, `game-lifecycle/fresh-game-state#idempotent-initialization`, `#identifiers-agree`). Seam: `game-lifecycle/launch-orchestration` invokes it — this change owns the mutation, not the call site, and the declared dependency on `game-lifecycle/fresh-game-state` is what makes the pairing visible in the graph
- [ ] 4.2 Severing tests in both directions: a team-scoped edit during a live game leaves the captured values and every portfolio untouched, and a game-scoped edit writes no team-scoped row (`bot-configuration/game-start-snapshot#in-progress-game-unaffected`, `#game-scoped-values-fork-from-defaults`, `bot-configuration/any-member-live-editing#edits-never-touch-team-defaults`)
- [ ] 4.3 One shared intersection module — the operable set is the team's configuration rows joined against the hosting build's registry — consumed by both the framework and the operator UI, classifying each row operable / stale / registered-but-unconfigured; the framework evaluates only the operable set and treats a stale row as inert (`bot-configuration/registry-defines-availability`, `#unconfigured-registry-entries-not-offered`, `#stale-rows-retained-not-deleted`). Record explicitly that Convex holds no registry and therefore cannot reject a synthetic Drive insert for an unregistered identifier — such a row is inert by the intersection rather than rejected at the contract — and confirm with the author that interface-level exclusion is the intended enforcement grain (`#no-unregistered-drive-affordance`)

## 5. Portfolio editing and effective-value derivation

- [ ] 5.1 The portfolio mutation surface in the component, wrapped in `packages/convex-host/` behind a current-member-of-the-owning-team gate: add a Drive with its target, remove a Drive, retarget a Drive, change a Drive or Preference weight, toggle a Preference's activation, set or clear the temperature override — plus, behind the same gate, the game-scoped temperature adjustment (`bot-configuration/any-member-live-editing`, `#any-member-not-only-captain`, `#game-scoped-parameters-need-no-captain`). Note that retargeting has no legacy mutation — decide whether it is a first-class mutation or a remove-then-add, and keep it one transaction either way
- [ ] 5.2 Persistence discipline: both omission causes are evaluated at evaluation time and neither is stored — a Drive whose target no longer resolves and a Drive the automated player has retired on satisfaction each stop contributing while its row survives untouched, and each resumes by itself when the condition lifts; the platform never deletes or deactivates a Drive row, and no turn transition, selection change, or deselection writes to any portfolio row (`bot-configuration/per-snake-portfolio-record`, `#dead-target-omits-never-deletes`, `#satisfied-drive-keeps-its-record`, `#temperature-override-survives-deselection`). Seam: retirement itself is `bot-framework/drive-satisfaction`'s and happens in the framework's memory — assert here that it produces no mutation
- [ ] 5.3 The effective-configuration overlay as one pure module over the captured defaults and a portfolio record — field-by-field, override wins where present — consumed by the framework, the operator UI, and any auditor from persisted state alone with no additional channel (`bot-configuration/effective-configuration`, `#override-wins-field-by-field`, `#derivable-by-any-reader`)
- [ ] 5.4 The effective-temperature derivation in the same module: the snake's override when set, otherwise the team's game-scoped temperature value, recomputed at each sampling decision with no cached derived value, delivered to the framework as the single opaque scalar of its portfolio contract; plus a test pinning the calibration direction — lower concentrates sampling on the best-scoring directions, higher flattens it (`bot-configuration/effective-temperature`, `#override-else-team-value`, `#change-applies-at-next-decision`, `#lower-is-more-deterministic`). Seam: `bot-framework/softmax-decision` consumes the scalar and owns the sampling itself
- [ ] 5.5 Reachability of live edits: the framework's portfolio mirror observes portfolio mutations through its existing reactive subscription and the snake's scores reflect the edit within the same turn without a restart and without the turn's accumulated evaluation being discarded, verified by an integration test at the seam (`bot-configuration/any-member-live-editing#weight-edit-keeps-evaluated-work`). Assert the observable pair only — evaluated work retained and updated scores visible without waiting out a fresh evaluation cycle — never that a particular world was or was not re-simulated: how the rescore is delivered is `bot-framework`'s machinery (`bot-framework/turn-scoped-evaluation`, `bot-framework/reactive-inputs`)

## 6. Operator-facing configuration surfaces (`apps/centaur-server-reference/`)

- [ ] 6.1 The heuristic configuration page: lists every configuration row with its classification, edits per Preference the active-by-default flag and default weight and per Drive type the default weight, nickname, and pinned status and order, marks stale rows visibly with a captain-only delete affordance, shows every affordance disabled for a non-captain, and states persistently that edits configure future games only (`bot-configuration/team-configuration-surfaces`, `#read-only-below-captain`, `bot-configuration/registry-defines-availability#stale-rows-retained-not-deleted`, `bot-configuration/game-start-snapshot#surfaces-say-future-games-only`)
- [ ] 6.2 The bot parameters page: edits the temperature default and the three submission-timing parameters, carries the same future-games-only statement, and exposes no game-rules parameter (`bot-configuration/team-configuration-surfaces`, `#no-game-rules-here`). Seam: the game's rules configuration is `game-configuration`'s surface and must not be reachable from here
- [ ] 6.3 Run the registry sync on a captain's visit to the heuristic configuration page, surfacing the newly inserted identifiers to the captain; a non-captain visit invokes nothing (`bot-configuration/registry-sync-insert-only#captain-visit-adopts-new-heuristics`)
- [ ] 6.4 Test that both surfaces write team-scoped rows only — no game-scoped or per-snake row changes whatever is edited (`bot-configuration/team-configuration-surfaces#pages-cannot-touch-games`)
- [ ] 6.5 The in-game Drive chooser: offers exactly the operable Drive types, ordered pinned-first in the captain's stored order then lexicographically by nickname with identifier as tiebreak, identical on every member's client because the ordering is team configuration (`bot-configuration/drive-management-interface#pinned-first-ordering`, `bot-configuration/registry-defines-availability#no-unregistered-drive-affordance`)
- [ ] 6.6 Targeting mode: highlight exactly the targets the Drive's eligibility predicate accepts and dim the rest, deterministic nearest-first keyboard cycling (the concrete tiebreak keys in code with a `// design:` reference, the binding promise being determinism and nearest-first), confirmation of an eligible target adds the Drive at its default weight with no further step, and cancellation leaves no trace (`bot-configuration/drive-management-interface`, `#only-eligible-targets-confirmable`, `#deterministic-cycling`, `#single-click-commits`, `#cancel-leaves-no-trace`)
- [ ] 6.7 The Drive list on the snake's panel: targets and weights shown, weight-editable and removable, every edit dispatched immediately, and a Drive currently omitted from play kept in the list marked as not contributing with its reason distinguished — unresolvable target versus satisfied motivation — rather than dropped (`bot-configuration/drive-management-interface`, `#omitted-drives-stay-visible`). Both classifications are computed client-side from the shared registry module and the observed board, the same intersection module section 4.3 builds; neither is read from a stored flag. Seams: the live interface shell hosting this panel is `operator-control/live-interface-availability`'s, and `decision-transparency/decision-breakdown` consumes this capability's portfolio and effective configuration for rendering — named here, built there
