- [ ] 1.4 Confirm with the author that the SpacetimeDB provisioning/management control plane is **out** of this capability's scope: it is an outbound third-party surface, and `game-lifecycle/instance-provisioning-authority` now owns its authority model (the platform signs its own credential per call and stores none, with the creation route restricted at the network boundary). ## 2. Integration-client records and registration (Convex — `packages/convex-snek-platform/`)

- [ ] 2.1 Client record and table: the client's own issuer identifier, the location at which it publishes its verification material, its human-chosen label, its capability ceiling, the registering admin's user record, creation timestamp, and nullable revocation timestamp. Records are never deleted. This replaces the scaffolded `ApiKeyRecord` in `packages/convex-snek-platform/src/index.ts` wholesale — there is no key material, no digest, and nothing secret to store (`platform-integrations/integration-clients`, `#nothing-secret-is-created-to-register`, `platform-integrations/client-management#revoked-records-retained`)
- [ ] 2.2 Registration mutation: admin-gated, recording the client as a principal in its own right rather than as an extension of the registering admin — its authority comes from its recorded ceiling, not from who registered it, and it does not inherit or track that admin's standing (`platform-integrations/integration-clients#a-client-is-not-its-registrar`). Registration returns nothing to keep secret: there is no plaintext moment, because the client generated its own key and the platform records only where the public half is published (`platform-integrations/client-registration#nothing-to-disclose-at-creation`)
- [ ] 2.3 Reject every call from a principal whose registration is absent or revoked, before any capability is considered — an unregistered issuer is not merely unauthorized, it is unknown (`platform-integrations/integration-clients#unregistered-caller-refused`)
- [ ] 2.4 Revocation mutation: takes effect on the very next call presenting a credential from that client, retains the record for audit, and cascades in the same transaction to every webhook subscription the client owns (`platform-integrations/client-management#revocation-immediate`, `#revoked-records-retained`, `platform-integrations/webhook-subscriptions#revoked-with-owning-client`). Note the coupling this replaces: authority now ends when the *client's registration* is revoked, never when a human's role changes, so nothing keeps delivering after a revocation
- [ ] 2.5 Enforce a client's negative bounds structurally rather than by per-handler checks — no reachable path makes a client a gameplay actor, creates or issues credentials for a human identity, or changes authentication configuration, and a client's ceiling cannot be widened into them regardless of what a user it acts for could do directly. The absence of the affordance is the enforcement (`platform-integrations/client-capability-bounds`, `#never-a-gameplay-actor`, `#no-identity-creation`, `identity-and-authorization/peer-capability-ceiling#ceiling-sits-below-the-user`)
- [ ] 2.6 Ceiling maintenance and its floor: a registered client's ceiling is editable by an admin and is the recorded upper bound every issuance intersects against, with a positive case pinned — a roster-management system's ceiling reaches the team and membership operations it exists for and nothing further (`platform-integrations/client-capability-bounds#a-roster-system-may-run-its-rosters`, `platform-integrations/client-management`)

## 3. The function surface (Convex deployment — `packages/convex-host/`)

- [ ] 3.1 Build no request surface. The deliverable of this section is the *absence* of a router, a versioned namespace, a payload schema layer, and a per-endpoint handler set: a registered client calls the platform's own public functions, and its capabilities name those functions. Assert it — a test or check that fails if an integration-specific inbound route appears (`platform-integrations/functions-are-the-api`, `#no-second-surface-to-keep-in-step`)
- [ ] 3.2 Declare the capability that reaches every function in the documented surface, and declare the **service-principal kind** on each — teams and membership, rooms and enrolment, reading a game and starting one, webhook subscriptions, client registrations. Human-only is the default a function departs from explicitly, so a function the surface promises but which omits the declaration is unreachable however broad the client's ceiling; the declaration is the reach (`platform-integrations/functions-are-the-api#the-families-are-a-floor`, `identity-and-authorization/principal-kind-gating#service-reach-is-declared-never-inferred`, `identity-and-authorization/capability-registry#naming-one-function-is-a-contract`)
- [ ] 3.3 A programmatic start enters `game-lifecycle/launch-orchestration` itself — the same gates, the same freeze, the same provisioning — so the resulting game is indistinguishable from a first-party start because it is the same function (`platform-integrations/functions-are-the-api#api-start-is-a-real-launch`)
- [ ] 3.4 Verify the parity that now follows structurally rather than being maintained: because both surfaces dispatch the same functions, no validation can exist in one path and not the other. Probe a representative set of invariants — a launched game's frozen configuration, the mid-game roster freeze, an archived entity — under equivalent authority and assert identical outcomes, and separately assert that a client whose ceiling reaches a function is still refused where the function's own authorization refuses (`platform-integrations/first-party-parity#no-privileged-bypass`, `#broad-ceiling-is-not-a-superuser`)
- [ ] 3.5 Pin the boundary of the promise: a function outside the documented surface accepting human identities alone refuses a client on principal kind, and that is a declared restriction rather than a family requiring fallback. Test one such refusal so the distinction is recorded in code, not just in prose (`platform-integrations/functions-are-the-api#outside-the-surface-is-not-a-fallback`)
- [ ] 3.6 Land the configuration edit inside the surface, as settled: the not-yet-launched game's configuration functions must declare the **service-principal kind** alongside the rest of the floor, so a client whose ceiling names them can set parameters and then start the game in one programmatic flow. The reach is the function's declaration, not a permission `game-configuration` grants — that capability gates nothing itself, its host supplies the access rules — so the only cross-capability ask is that the edit be a public platform function carrying the kind declaration; raise it with `game-configuration`'s owner rather than adding a gate there (`platform-integrations/functions-are-the-api#configuring-a-game-is-inside-the-surface`, `identity-and-authorization/principal-kind-gating#service-reach-is-declared-never-inferred`)
- [ ] 3.7 Settle the remaining surface question with the owning siblings before the capability declarations are frozen: what adding a team member by email does when no user record exists for that email, given that creating a human identity is prohibited (`accounts-and-profiles`, `team-management` own the resolution) (`platform-integrations/functions-are-the-api#the-families-are-a-floor`, `platform-integrations/client-capability-bounds#no-identity-creation`)

## 4. First-party client-management surface (`apps/centaur-server-reference/`)

- [ ] 4.1 Admin-only client management view: lists registered and revoked clients with label, issuer identifier, publication location, ceiling, and timestamps, with register, edit-ceiling, and revoke affordances, stating plainly that a client acts as itself under its recorded ceiling rather than as the admin who registered it (`platform-integrations/client-management`, `platform-integrations/integration-clients#a-client-is-not-its-registrar`)
- [ ] 4.2 Registration flow shows nothing to keep secret and never asks for a private key — it records where the client publishes its public material, and every view before and after renders metadata only. Assert there is no code path that could display a credential, because none exists to display (`platform-integrations/client-registration#nothing-to-disclose-at-creation`, `#metadata-only-ever-after`)
- [ ] 4.3 Confirm the surface's home is acceptable now that nothing secret crosses it. The earlier concern — the platform's most powerful credential minted and disclosed inside client code a team operator forks and runs — is answered by the model rather than by placement: registration creates no secret, so a forked deployment rendering this view discloses nothing. What remains is ordinary admin-gated management, subject to `global-invariants/access-follows-identity#reference-deployment-has-no-special-privilege` like every other view. Record that reasoning rather than re-litigating the placement (`platform-integrations/client-registration`)

## 5. Webhook subscriptions and delivery (Convex — `packages/convex-snek-platform/`)

- [ ] 5.1 `webhooks` table and record type: delivery URL, one or more event types from the closed set, a scope naming exactly one game or one room, the **owning integration client**, creation timestamp, and revocation state. This replaces the scaffolded `WebhookRecord` in `packages/convex-snek-platform/src/index.ts`, which binds to `ownerUserId` with no scope and no revocation field and so cannot express the record at all (`platform-integrations/webhook-subscriptions`)
- [ ] 5.2 Register, list, and delete subscriptions under client authorization, with room-scope matching resolved at event time against the room's then-current game, so a game newly hosted in the room is covered with no re-registration (`platform-integrations/webhook-subscriptions#room-scope-follows-the-room`)
- [ ] 5.3 Auto-revocation with the owning client's registration (the cascade of §2.4): no delivery for any event occurring after the revocation, including events already enqueued but not yet delivered, and no path by which a revoked client re-registers or resurrects a subscription (`platform-integrations/webhook-subscriptions#revoked-with-owning-client`)
- [ ] 5.4 Emit events from the game's **status transitions** rather than from the finish-notification handler, so `game_end` also covers a walkover that goes straight from `not-started` to `finished` and a finish forced by the stale-game fallback, and no event is emitted at record creation — including auto-created successors (`platform-integrations/lifecycle-event-notifications`, `#no-creation-event`; seam: `game-lifecycle/status-authority`, whose transition mutations this hooks)
- [ ] 5.5 Payload construction: `game_start` carries the game id, its room's id, and the launch-frozen configuration the game is actually played under; `game_end` carries the game id, its room's id, and the final scores. Confirm both are readable from the game record at emission time — the scaffolded `GameRecord` carries only `winnerTeamId`, not per-team final scores (seams: `game-configuration` for the frozen configuration's shape, `game-lifecycle`/`replay-and-audit` for the recorded outcome) (`platform-integrations/lifecycle-event-notifications#start-payload-is-the-played-config`)
- [ ] 5.6 Delivery worker with at-least-once semantics: retry on network failure, non-success response, or timeout with exponential backoff until success or a bounded budget is exhausted, then stop; each subscription's failures isolated so one dead endpoint delays no other subscription's deliveries. Retry counts and intervals are mechanism (`platform-integrations/at-least-once-delivery`, `#retries-back-off-and-stop`)
- [ ] 5.7 Deduplication identifier determined **solely** by the game, the event type, and the subscription — identical on every attempt and redelivery, never colliding across distinct events — with a test that pins stability across retries and asserts it is not derived from any per-attempt value (`platform-integrations/at-least-once-delivery#same-id-on-every-redelivery`)
- [ ] 5.8 Non-blocking delivery: enqueue after the lifecycle transaction commits and never await a delivery inside lifecycle handling, so a hanging or failing subscriber delays neither the transition to `playing`/`finished`, nor the record's persistence, nor the instance's teardown; test with a subscriber that never responds (`platform-integrations/non-blocking-delivery#unresponsive-subscriber-harmless`; seam: `game-lifecycle/teardown-after-persistence`)
- [ ] 5.9 Destination admission, implemented as one shared check called from two places: HTTPS-only, and the resolved address must be publicly routable — loopback, link-local, private ranges, the deployment's own origin, and the instance-provisioning host all refused. Call it at registration for the user-visible error, and call it again inside the delivery worker against the address the connection is about to open, since a hostname admitted at registration can be re-pointed afterwards (`platform-integrations/delivery-destination-admission#inward-aimed-destination-refused`, `#plaintext-destination-refused`, `#rechecked-against-the-address-actually-reached`)
- [ ] 5.10 Make the re-check unbypassable by the HTTP client itself: pin the connection to the address that was admitted rather than re-resolving after the check, and refuse redirects to an inadmissible destination. A delivery that fails admission is abandoned, not retried — it must not consume the retry budget of §5.6 or produce a backoff schedule of internal requests (`platform-integrations/delivery-destination-admission`, `platform-integrations/at-least-once-delivery#retries-back-off-and-stop`)
