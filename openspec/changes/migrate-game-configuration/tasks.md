- [ ] 1.3 Fix the component's mount-time shape before any UI is written: one explicit parameter per affordance kind — inspection, parameter editing, board designation — with the standalone dev mounting offering all three, and no actor, role, or access rule anywhere in the component's inputs (game-configuration/host-selected-affordances, game-configuration/self-contained-configuration-surface)
- [ ] 1.4 Confirm the one shared board-generation implementation runs inside a Convex mutation (BLAKE3 via `@noble/hashes`, Perlin noise, no ambient nondeterminism) and decide where the game's root seed is drawn from, given generation takes randomness only as an explicit input — mutation, action, or caller-supplied. It still ships inside `packages/engine/` and is extracted to a shared package in a later PR; nothing here depends on which package hosts it (game-configuration/board-generation-retry#reproducible-retries)
- [ ] 1.5 Raise the engine-side bounds export with the author as a `game-engine` request, now scoped to the **gameplay** parameters alone: today the bounds live only in `types.ts` field comments and in `CONFIG_RANGES` in `packages/engine/src/arbitraries.ts`, which is documented "not part of the package's public API" and is not re-exported from `src/index.ts` — this capability needs them as a public, reflectable descriptor (path, kind, min, max, default, sentinel) it can read rather than restate. The board-generation bounds are no longer part of that ask: the engine declares none, and this capability declares them itself in section 7 (game-configuration/parameter-bounds-sourcing, game-configuration/parameter-bounds-sourcing#live-game-bounds-are-reflected-not-owned)

## 2. Configuration record, vocabulary, and the engine mirror (Convex — `packages/convex-snek-platform`)

- [ ] 2.1 Add the configuration columns to the `games` table — the `config` document (the gameplay half the engine declares plus the board-generation half this capability declares), the single current-preview value, and the boolean lock — as the one record per game, initialised from the engine's exported `DEFAULT_GAME_CONFIG`; no configuration column on the room record (game-configuration/config-lives-on-the-game, game-configuration/closed-parameter-vocabulary)
- [ ] 2.2 Write the Convex `v.*` validator so its gameplay half is a field-for-field mirror of the engine's gameplay configuration type (`GameRuntimeConfig` in `packages/engine/src/types.ts`) while its board-generation half mirrors nothing and is this capability's own shape, guard it with the platform's **shared** mirror assertion rather than a check written here — the assertion is `mint-platform-persistence`'s and is exact type equality (the conditional-type identity trick), not mutual `extends`, which is blind to both `readonly` modifiers and the excess-field direction, since the engine's fields are all `readonly` and Convex's `Infer<>` yields mutable properties — and hand the stored document straight to the engine with no mapping layer, pinned by a test that generates a board and resolves a turn from a document read back out of the table verbatim (game-configuration/engine-schema-fidelity, global-invariants/engine-mirrors-are-guarded#one-assertion-every-site, game-configuration/engine-schema-fidelity#no-translation-at-handoff)
- [ ] 2.3 Implement authoritative range/type/sentinel validation at the record for every parameter, rejecting identically whatever the caller, with every gameplay threshold read from the engine's bounds descriptor (task 1.5) and every board-generation threshold read from this capability's own declaration (task 7.2) — no bound literal is written twice anywhere (game-configuration/closed-parameter-vocabulary, game-configuration/closed-parameter-vocabulary#out-of-range-rejected-regardless-of-client, game-configuration/parameter-bounds-sourcing, game-configuration/parameter-bounds-sourcing#widget-and-validator-agree)
- [ ] 2.4 Pin the vocabulary as closed: a test asserting the validator admits exactly the two halves of task 2.1 and no additional field, so no bot-behaviour, heuristic, or Drive parameter can be added to it (game-configuration/closed-parameter-vocabulary#no-bot-parameters)
- [ ] 2.5 Encode disablement solely by the zero sentinels the two halves declare — no auxiliary gating flags in the schema — and accept and persist any in-range dependent value regardless of its gate; the "ignored while gated" half is already engine behaviour (`boardgen.ts` fertile-ground gate, `win.ts` turn cap, spawn rates) and needs a citation, not new code (game-configuration/conditional-parameter-semantics, game-configuration/conditional-parameter-semantics#gated-value-persists-and-is-ignored)
- [ ] 2.6 Guard the edit window and the one-open-game exclusivity inside the transaction of every configuration write — reject writes to a game that has launched or finished without launching, and admit an edit arriving moments before a concurrently committing launch on exactly one side of the freeze (game-configuration/launch-freeze, game-configuration/launch-freeze#post-launch-writes-rejected, game-configuration/launch-freeze#editable-until-launch, game-configuration/config-lives-on-the-game#one-game-configured-at-a-time)
- [ ] 2.7 Implement the roster-contextual tightening of board-generation bounds — the effective limit on snakes per team and board size given how many teams must be seated — as a derivation over **this capability's own** declared range (task 7.2), never a widening of it, and assert in a test that the tightened limit is always within the declared one. There is no engine-declared outer limit underneath any more, which removes the reconciliation the earlier shape needed rather than adding one (game-configuration/parameter-bounds-sourcing, game-configuration/parameter-bounds-sourcing#roster-tightens-generation-bounds)

- [ ] 2.8 Enforce the at-least-one-limit condition as a cross-field guard inside the transaction of every configuration write, and again at the launch gate: a write that would leave the record with neither the turn limit nor the wall-clock duration limit is rejected. It cannot be expressed as a range on either parameter, so it is a check over the document rather than an entry in the per-field validator of task 2.3 (game-configuration/bounded-game-duration, game-configuration/bounded-game-duration#neither-limit-is-rejected, game-configuration/bounded-game-duration#launch-cannot-freeze-an-unbounded-game)
- [ ] 2.9 Test both single-limit configurations as complete on their own, and the edit-ordering consequence the guard produces: setting the duration limit and then disabling the turn limit succeeds, while the reverse order is refused at the first write (game-configuration/bounded-game-duration#a-turn-limit-alone-is-valid, game-configuration/bounded-game-duration#a-duration-limit-alone-is-valid, game-configuration/bounded-game-duration#switching-which-limit-applies)

## 3. Board preview and lock-in (Convex — `packages/convex-snek-platform`)

- [ ] 3.1 Preview regeneration: run the one shared board-generation implementation platform-side against the game's current parameters and roster and a fresh seed — the same entry point the launch path calls, not a copy of it — overwriting the single current-preview value with no candidate history, reactively readable by every configuration surface, and writing only to the not-yet-launched game being configured (game-configuration/board-preview, game-configuration/board-preview#one-slot-no-archive, game-configuration/board-preview#all-viewers-in-sync, game-configuration/board-preview#a-playing-game-is-never-touched, global-invariants/one-shared-generation#preview-and-launch-are-one-implementation)
- [ ] 3.2 Derive the regeneration trigger from the engine's generation inputs rather than a hand-listed set — the board-generation subtree plus the team registrations — and clear the lock in the same transaction as the change that regenerates the preview (game-configuration/board-preview, game-configuration/board-preview-lock-in#board-affecting-edit-clears-the-lock)
- [ ] 3.3 Lock mutation carrying no board data — a boolean designating the platform-held current preview, settable and clearable freely while the game awaits launch, ignoring any client-supplied board payload (game-configuration/board-preview-lock-in, game-configuration/board-preview-lock-in#lock-carries-no-board-data, game-configuration/board-preview-lock-in#lock-toggles-freely-before-launch)
- [ ] 3.4 Record and reactively deliver generation's structured infeasibility failure, mapping its three failure codes and detail fields to the named constraint that failed; the bounded-retry and structured-error implementation already exists (`boardgen.ts`, `BoardGenerationFailure`) and needs only a citation (game-configuration/infeasibility-surfaced, game-configuration/infeasibility-surfaced#failure-names-the-constraint, game-configuration/board-generation-retry#infeasible-configuration)
- [ ] 3.5 Wire roster changes into the same path as parameter edits: a change in the number of players or the composition of teams regenerates the preview and clears any standing lock, in the transaction of the enrolment change itself (seam: rooms-and-matchmaking/team-enrolment) — with a test that an enrolment change alone, no parameter touched, both regenerates and unlocks (game-configuration/board-preview#roster-change-regenerates, game-configuration/board-preview-lock-in#roster-change-clears-the-lock)

- [ ] 3.6 Test the other side of the trigger: editing a parameter generation does not read — the turn limit, the wall-clock duration limit, a clock value, hazard damage — neither regenerates the preview nor clears a standing lock. This is a consequence of deriving the trigger from the generation inputs (task 3.2) rather than from "any parameter edit", and is worth a test precisely because the wrong implementation passes every other preview test (game-configuration/board-preview-lock-in#a-dynamic-gameplay-edit-leaves-the-lock-standing)

## 4. The generation-parameter boundary (Convex handoff + `packages/stdb`)

- [ ] 4.1 Author the boundary as a payload contract — only the dynamic gameplay subtree plus the precomputed initial state cross to the per-game runtime — with a test over the payload builder asserting no board-generation field appears in it; the call site is game-lifecycle/instance-initialization, so this is the contract plus its test, not the orchestration (game-configuration/generation-parameter-boundary, game-configuration/generation-parameter-boundary#only-the-gameplay-subtree-crosses)
- [ ] 4.2 Delete the parallel configuration type in `packages/stdb/src/index.ts` (`GameConfig` with `boardSize: string`, `hazardPercent`, `fertileGround: boolean`, and `snakesPerTeam`) and re-export the engine's runtime configuration type instead — as written it is both a second implementation of the engine's vocabulary and a channel carrying board-generation parameters into the runtime; in the same pass keep the runtime generation-free — no board-generation import in `packages/stdb`, and the delivered starting state used as-is (game-configuration/engine-schema-fidelity, game-configuration/generation-parameter-boundary#only-the-gameplay-subtree-crosses, game-configuration/generation-parameter-boundary#the-runtime-never-generates)
- [ ] 4.3 Pin the platform-side generation call shape: the generation entry point takes the whole configuration (it reads maximum health from the gameplay subtree to initialise snakes, a documented deviation in `boardgen.ts`), so "board-generation parameters are consumed platform-side" must not be implemented as passing only the board-generation half to it (game-configuration/generation-parameter-boundary, game-configuration/initial-snakes#initial-state)

- [ ] 4.4 Keep the platform to one generator while the boundary is being wired: the preview mutation of section 3 and the launch path that generates for an unlocked game reach the same entry point, and the standalone dev mounting of section 5 is handed a board rather than growing one of its own. The single-implementation rule and its guard are `mint-platform-persistence`'s (seam); what belongs here is that neither of this capability's two generation call sites becomes the second implementation (game-configuration/generation-parameter-boundary, global-invariants/one-shared-generation, global-invariants/one-shared-generation#preview-and-launch-are-one-implementation)

## 5. The configuration component and its standalone delivery

- [ ] 6.2 Close the residual launch-time arm of the locked-board-versus-seated-roster conflict: an enrolment change now clears the lock, but a standing lock plus a team server that declines to seat at launch still leaves a designated board for a roster that will not materialise — decide with the author whether the launch gate refuses, re-generates, or seats fewer teams (seams: game-lifecycle/instance-initialization, game-lifecycle/launch-gates) (game-configuration/board-preview-lock-in)
- [ ] 6.3 Confirm the configuration contract is reachable through the programmatic surface with the same validation and the same freeze — a registered client calls these same functions, so parity is structural provided the functions declare the service-principal kind where the documented surface needs them to (seam: platform-integrations/functions-are-the-api, platform-integrations/first-party-parity, identity-and-authorization/principal-kind-gating) (game-configuration/closed-parameter-vocabulary#out-of-range-rejected-regardless-of-client)
- [ ] 6.4 Hand the affordance-kind seam to the room story: rooms-and-matchmaking mounts this component in the room context and maps its own actors onto the three kinds, which is where access rules over configuration are defined — nothing in this capability changes when it does (seam: rooms-and-matchmaking/room-lobby) (game-configuration/host-selected-affordances)

- [ ] 6.5 Close the duration-limit loop across its three owners: the parameter is declared *and evaluated* by the engine (`revise-game-engine-contract`, which folds first), it crosses to the per-game runtime inside the gameplay subtree and nowhere else, and the runtime's part is only to measure what each turn cost and supply it — confirm the payload carries the parameter and that a game ended by the limit is finished through the ordinary terminal path, which is also what makes the staleness bound downstream a finite quantity (seams: `revise-game-engine-contract`, game-runtime/turn-timing-measurement, game-lifecycle/stale-game-recovery) (game-configuration/bounded-game-duration, game-configuration/generation-parameter-boundary#only-the-gameplay-subtree-crosses)

## 7. The board-generation rules this capability now owns

Six requirements moved here from `game-engine` in the same change that removed them (`revise-game-engine-contract`), joined by two this capability had to author itself: the generation parameter vocabulary the engine no longer declares, and the generated board's shape. The algorithm still lives in `packages/engine/src/boardgen.ts` and moves in a later PR — nothing below moves code.

- [ ] 7.1 Cite the existing generation implementation against its new identifiers rather than rewriting it: the six moved requirements describe `boardgen.ts` and `perlin.ts` as they already stand, stage for stage, so this section is a re-homing of the contract and a sweep of `// spec:` comments, not new behaviour (game-configuration/hazards, game-configuration/fertile-ground, game-configuration/starting-placement, game-configuration/initial-snakes, game-configuration/initial-food, game-configuration/board-generation-retry)
- [ ] 7.2 Declare the five board-generation parameters as this capability's own data — path, kind, min, max, default, sentinel — in the same reflectable shape the engine's descriptor uses for the gameplay half, so a widget or a validator reads two tables of one shape rather than one table and a hardcoded remainder. There is no engine range beneath these to defer to (game-configuration/generation-parameters, game-configuration/generation-parameters#generation-parameters-are-declared-here, game-configuration/parameter-bounds-sourcing)
- [ ] 7.3 Test the sentinels against the generator that already implements them: `hazardPercentage` 0 designates no Hazard cell, `fertileGround.density` 0 designates no Fertile cell and leaves clustering inert — behaviour `boardgen.ts` already has, which needs a citation and a test rather than code (game-configuration/generation-parameters#generation-sentinels, game-configuration/conditional-parameter-semantics#gated-value-persists-and-is-ignored)
- [ ] 7.4 Pin the wall ring where it is now owned: generation emits the complete ring, and the engine neither rebuilds nor requires it (leaving the grid resolves exactly as hitting a wall). Test the ring on generated boards here rather than in the engine's suite, where it is no longer a claim the engine makes (game-configuration/generated-board-shape#complete-wall-ring, game-configuration/generated-board-shape#the-ring-is-generations-to-supply)
- [ ] 7.5 Keep the two halves of the vocabulary disjoint in the schema itself, so the drift guard of task 2.2 can hold the boundary in both directions — an engine field appearing in the generation half, or a generation field appearing in the gameplay half, fails the build (game-configuration/engine-schema-fidelity#a-generation-field-is-not-a-mirror-failure, game-configuration/closed-parameter-vocabulary)
- [ ] 7.6 Confirm the initial state is self-describing before it leaves the platform: the board's dimensions state its size and the placed snakes state each team's count, so nothing downstream needs a generation parameter to interpret what it was sent — which is what makes the boundary of section 4 a payload rule rather than a convention (game-configuration/initial-snakes#the-count-travels-in-the-snakes, game-configuration/generation-parameter-boundary#only-the-gameplay-subtree-crosses)
