# migrate-accounts-and-profiles — Tasks

## 1. Pre-implementation

- [ ] 1.1 Review this change's artifacts with the author immediately before implementation begins, and refine this task breakdown then
- [ ] 1.2 Seam gate — declared dependencies: this capability sits near the top of the graph and cannot begin before `identity-and-authorization` (sign-in, identity resolution, authentication, mutation authorization), `team-management` (team record, roster, captaincy, archive-not-delete, management view), `replay-and-audit` (`team-game-history`'s historical-or-current eligibility rule and normalised-score headline convention, `finished-games-public`), `game-lifecycle` (`game-record`, `roster-snapshot`, `finish-notification`), `rooms-and-matchmaking` (`room-record`) have landed; `global-invariants` and `game-engine/scoring` are already folded. Two capabilities this delta does not declare are implementation prerequisites all the same: `application-shell` (the one application §6's surfaces mount into, which folds ahead of every capability owning a view) and `platform-persistence` (the component boundary §2–§5's Convex work sits behind). Because `replay-and-audit` itself sits behind eight capabilities, this change is deep in the train's fold order — but no longer last: `tournaments` declares this capability (its forfeit-reporting obligation reaches `leaderboard`, `player-profile` and `team-profile`), so it folds after this one. Confirm that ordering with the author
- [ ] 1.3 Seam gate, mostly settled: the historical layer's two undeclared sources are now declared dependencies — `game-lifecycle` for the participating-team snapshot, the recorded outcome and the final scores, `rooms-and-matchmaking` for the room record the listings label games with and the room-scoped ranking filters on — and the requirements resting on them carry the entries. What remains open is the third: the team profile presents a server health status whose recording semantics are `team-server-management/server-healthcheck`'s, a live-state display rather than part of the historical layer. Decide with the author at implementation whether that read warrants adding `team-server-management` to the Purpose or the profile should link onward to the team-server surface instead (`accounts-and-profiles/team-profile`)

## 2. Persistent user record (Convex platform component)

- [ ] 2.1 Define the `users` table in `packages/convex-snek-platform/schema.ts` — the platform-assigned identifier that is the record's identity, display name, contact email, first-authentication timestamp — replacing the placeholder stub that already carries this capability's citation. No provider subject and no provider-keyed index belong on this table: authentication resolves through the linkage record `identity-and-authorization` owns, which retires the stub's `googleSub` field (`accounts-and-profiles/user-record`, seam: `identity-and-authorization/linked-provider-credentials#the-linkage-is-the-only-lookup`)
- [ ] 2.2 Bind the record to its identity for life: expose a create-if-absent the sign-in mutation calls inside its own transaction, and keep the platform-assigned identifier immutable while display name and contact email stay ordinary editable attributes — updating either updates the record in place and forks nothing. The sign-in flow and who counts as the same human are `identity-and-authorization`'s, and so is the guard deciding two racing first sign-ins: it is the linkage's uniqueness check, not a second guard over this table. This side owes the create-if-absent and a test of the outcome (`accounts-and-profiles/user-record#created-at-first-sign-in`, `#attributes-change-the-identifier-does-not`, seam: `identity-and-authorization/linked-provider-credentials#one-provider-account-one-person-forever`)
- [ ] 2.3 Implement permanence as the absence of a path: no delete, no merge, no expiry or dormancy cleanup over user records anywhere in the platform component or the host, with tests asserting attribution survives loss of the underlying Google account and that no operation folds one record's memberships, attributions or statistics into another (`accounts-and-profiles/user-record-permanence#lost-account-deletes-nothing`, `#never-merged`)
- [ ] 2.4 Decide whether a user record carries any archived/dormant flag at all: the legacy schema design had one on `users`, and nothing in this delta gives it meaning. Either drop it or give it a stated meaning that cannot be read as deletion (`accounts-and-profiles/user-record-permanence`)

## 3. Data-contract rules: email confidentiality and the authenticated-only surface

- [ ] 3.1 Define one user-facing user projection in `packages/convex-snek-platform/` whose type structurally cannot carry the email, route every user-facing query, subscription and exported record shape through it — the field absent from the shape, never returned and hidden — and add a mechanised guard (test or type-level assertion over the exported shapes) so a *new* view built on the same shape cannot leak either (`accounts-and-profiles/email-confidentiality#omitted-at-the-boundary`, `#hidden-even-from-self-view`)
- [ ] 3.2 Confine email reads to the identity-matching and administrative paths that need them, and add no user-facing surface exposing an email — including for platform admins, since this delta mints no such view (`accounts-and-profiles/email-confidentiality`)
- [ ] 3.3 Enforce email-free participation snapshots: the per-game snapshot stores user references only, and display names resolve through the email-free projection. The snapshot record is `game-lifecycle/roster-snapshot`'s — land this as a shape constraint plus a regression test over its validator, not as a second owner of the snapshot (`accounts-and-profiles/email-confidentiality#participation-snapshots-are-email-free`)
- [ ] 3.4 Gate every query behind this capability at the Convex function contract in `packages/convex-host/`, never in the app's routing, so an unauthenticated visitor can reach, index or enumerate none of it and a fork cannot open it; the authentication requirement itself is `identity-and-authorization/authentication-required`'s (`accounts-and-profiles/no-public-surface#unauthenticated-visitors-see-nothing`)
- [ ] 3.5 Impose no second gate among authenticated users on any profile, statistic, history or leaderboard read — membership, role and standing scope discovery only — and keep the reference app's unauthenticated route exemption list to sign-in, sign-out and static assets, matching the empty public carve-out (`accounts-and-profiles/no-public-surface#authenticated-users-face-no-further-gate`)

## 4. Snapshot attribution, history listings and aggregate statistics (Convex query layer)

- [ ] 4.1 Build the historical-presentation query layer — the platform component's own functions in `packages/convex-snek-platform/`, auth-wrapped for callers by `packages/convex-host/`, which holds no table of its own (§5's leaderboard queries likewise; seam: `platform-persistence/component-boundaries#the-host-adds-authority-not-storage`) — so every listed participant, opponent, result and score resolves from the game's participating-team snapshot and the recorded outcome, with no read of current team or membership records on any historical path, and so archiving is inert for presentation — an archived team or opponent renders under its historical identity with nothing recomputed (`accounts-and-profiles/snapshot-attribution#team-of-the-day`, `#roster-changes-rewrite-nothing`, `#head-to-head-archive-stable`)
- [ ] 4.2 Generalise `replay-and-audit`'s per-hosted-team history query into one shared, scope-parameterised listing query — it lands first, so this is an extension, never a second implementation — serving the player profile and the team profile too, and compute each profile's aggregate statistics from exactly that query's result set rather than recomputing independently, so the eligibility rule, the normalised-score headline and the statistics/listing agreement exist once and cannot drift between surfaces. Keep the scopes distinct: the historical-or-current membership predicate scopes the player profile and `replay-and-audit`'s page, while the team profile's history is the team's complete one and is viewer-scoped by nothing (`accounts-and-profiles/player-profile#history-outlives-membership`, `accounts-and-profiles/team-profile#full-history-for-any-viewer`, `accounts-and-profiles/aggregate-statistics#consistent-with-the-listing`, seam: `replay-and-audit/team-game-history#historical-or-current-membership`)
- [ ] 4.3 Produce the required aggregates — player: games played, win rate, average team score; team: games played, win rate, average score, head-to-head against every distinct opponent with none omitted — all on the normalised score. Settle one consequence with the author before building the player aggregates: the player listing includes games a current team played before the viewer joined, and the statistics must agree with the listing, so a player's games played and win rate as specified count games they were not in — decide whether the listing narrows or the statistics diverge, and record it (`accounts-and-profiles/aggregate-statistics`, `#consistent-with-the-listing`, `accounts-and-profiles/player-profile`)
- [ ] 4.4 Compute head-to-head pairwise: a game with N competing teams contributes N−1 entries per participant, each settled by comparing just those two teams' final scores in that game and never by who won the game overall — so an opponent met only in three- and four-team games is still recorded, and a team may hold a winning record against a team that placed above it. Test the two-team case and a four-team case together so the general rule is what ships (`accounts-and-profiles/aggregate-statistics#pairwise-inside-a-multi-team-game`, `#head-to-head-covers-every-opponent`, seam: `game-engine/scoring`)
- [ ] 4.5 Implement the presented-game predicate once, in the shared listing query of §4.2, so every history, statistic, head-to-head and ranking is drawn from the same set: finished games carrying a recorded outcome. A game finished by failure with no scores recorded is excluded from listing and aggregate identically; a game decided without play but carrying an outcome is included. Test that the exclusion cannot be applied on one side only. The rule binds this capability's surfaces; whether `replay-and-audit`'s own history page adopts it is that capability's call, so make it a parameter of the shared query rather than a fact baked into it (`accounts-and-profiles/recorded-outcomes-only#a-failed-game-counts-nowhere`, `#decided-without-play-still-counts`, `accounts-and-profiles/aggregate-statistics#consistent-with-the-listing`, seam: `game-lifecycle/finish-notification#error-outcome-still-finishes`)

## 5. Leaderboard (Convex query layer)

- [ ] 5.1 Model the ranking criteria and time windows as exhaustive closed unions — win rate with a qualifying threshold, total wins, average normalised score; all time, last 30 days, last 7 days — so adding one is a compile error until the requirement is revised, and implement criterion switching and window filtering over the snapshot-resolved game set. Close the *criterion* and *window* unions only: leave a ranked entry's rendered content open to extension, so a downstream capability requiring an annotation on an entry needs no revision here (`accounts-and-profiles/leaderboard#closed-sets-only`)
- [ ] 5.2 Implement the optional single-room restriction such that every criterion and window is recomputed over that subset alone, never filtered after ranking (`accounts-and-profiles/leaderboard#room-scoped-ranking`)
- [ ] 5.3 Keep archived teams in the default ranking under their archived identity — rendered as archived rather than indistinguishable from a live team, which is the render half `global-invariants/client-truthfulness#archived-teams-still-render` already owns and this capability does not restate — with nothing recomputed, and verify no other team's standing shifts when a rival archives (`accounts-and-profiles/leaderboard#archived-teams-still-ranked`)
- [ ] 5.4 Feed forfeited games into every criterion as games the team played, taking the score from the one shared scoring implementation rather than special-casing a value here — games played, the qualifying threshold, win rate and average score all include them. Test that a team's standing does not improve by forfeiting rather than losing. Scope: the ranking treatment only — *labelling* a forfeited game as a forfeit on an entry, a profile history or any other presentation is required by `tournaments/forfeit-scoring#forfeit-visible-downstream` and arrives as a diff to these surfaces authored with that capability; this change neither implements nor restates it (`accounts-and-profiles/leaderboard#forfeits-rank-rather-than-vanish`, seam: `game-engine/scoring#forfeit-exclusion`)
- [ ] 5.5 Choose the minimum-games qualifying threshold value and record it as a tuning parameter with a `// design:` reference to this change — its existence is spec, its value deliberately is not (`accounts-and-profiles/leaderboard`)

## 6. Web surfaces (apps/centaur-server-reference)

- [ ] 6.1 Extend the application's existing navigation frame with this capability's platform-scoped entries — home, the teams browser, the viewer's own profile, the leaderboard — rather than standing up a shell of its own: the frame is `application-shell`'s mechanism and lands first. Then build the home view on it: the user's current teams, recently visited rooms, and the in-progress games of the user's own teams, every entry a direct link — a link into another team's team-internal live surface resolving to that team's home server, everything else served locally. Home stays user-scoped; platform-wide live-game discovery is the Room Browser's and is not duplicated here. The recently-visited-rooms memory shape is plastic, but its home is not — it is per-user platform state, never client-persisted, or the same user sees different rooms on two servers (`accounts-and-profiles/home-view#live-participation-surfaces`, `#home-links-onward`, seams: `application-shell/unified-web-application`, `team-server-management/shared-hosting#cross-server-links-resolve-the-home`, `rooms-and-matchmaking/room-discovery#live-games-found-through-the-browser`)
- [ ] 6.2 Build the teams browser: name, display colour and current captain per team, archived teams absent from the default listing while their profiles stay reachable, every entry opening the team profile (`accounts-and-profiles/teams-browser#entry-opens-the-profile`, `#archived-hidden-not-gone`)
- [ ] 6.3 Build the player profile view for every user record — reachable from global navigation for oneself and linked from member listings and game histories — showing display name, memberships, and the snapshot-scoped chronological history with room, date, participating teams, result and scores (`accounts-and-profiles/player-profile#every-user-has-one`, `#history-outlives-membership`)
- [ ] 6.4 Derive the profile's "teams played for" from the participating-team snapshots that list the user — not from every game the listing carries, which also holds a current team's games from before they joined. No membership-history record is created here or asked of `team-management`, whose roster stays current-membership-only with no soft-deleted rows standing in for history. Test the accepted limitation explicitly so nobody later "fixes" it: a user who joined and left a team with no game played in between shows that team nowhere once gone (`accounts-and-profiles/player-profile#past-teams-are-teams-played-for`, seams: `game-lifecycle/roster-snapshot`, `team-management/roster-of-operators#the-roster-is-not-a-history`)
- [ ] 6.5 Build the team profile view for every team, archived included: identity, current roster, captain, server nomination with latest recorded health status, full chronological history and statistics, with no mutating affordance — at most a link onward to the management surface where authority is enforced. Two seams keep that read-only-ness structural rather than remembered: mount the view against a binding with no mutation to express, and show the health status as the latest on-demand result with its timestamp — this view triggers no check, since recording and triggering are both `team-server-management`'s (`accounts-and-profiles/team-profile#full-history-for-any-viewer`, `#strictly-informational`, `#archived-teams-keep-their-profile`, seams: `application-shell/one-state-binding#absence-not-refusal`, `team-server-management/server-healthcheck#on-demand-not-polled`)
- [ ] 6.6 Build the leaderboard view with criterion and window controls, the optional room restriction, and each ranked entry linking to its team profile (`accounts-and-profiles/leaderboard`)
