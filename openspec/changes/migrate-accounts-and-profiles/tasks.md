## 2. Persistent user record (Convex platform component)

- [ ] 2.1 Define the `users` table in `packages/convex-snek-platform/schema.ts` — the platform-assigned identifier that is the record's identity, display name, contact email, first-authentication timestamp, plus the index the identity lookup needs — replacing the placeholder stub that already carries this capability's citation (`accounts-and-profiles/user-record`)
- [ ] 2.2 Bind the record to its identity for life: create it at first successful sign-in as a query-then-guard upsert inside the same mutation as the insert so two racing first sign-ins yield exactly one record, and keep the platform-assigned identifier immutable while display name and contact email stay ordinary editable attributes — updating either updates the record in place and forks nothing. The sign-in flow and who counts as the same human are `identity-and-authorization`'s (`accounts-and-profiles/user-record#created-at-first-sign-in`, `#attributes-change-the-identifier-does-not`)
- [ ] 2.3 Implement permanence as the absence of a path: no delete, no merge, no expiry or dormancy cleanup over user records anywhere in the platform component or the host, with tests asserting attribution survives loss of the underlying Google account and that no operation folds one record's memberships, attributions or statistics into another (`accounts-and-profiles/user-record-permanence#lost-account-deletes-nothing`, `#never-merged`)
- [ ] 2.4 Decide whether a user record carries any archived/dormant flag at all: the legacy schema design had one on `users`, and nothing in this delta gives it meaning. Either drop it or give it a stated meaning that cannot be read as deletion (`accounts-and-profiles/user-record-permanence`)

## 3. Data-contract rules: email confidentiality and the authenticated-only surface

- [ ] 3.1 Define one user-facing user projection in `packages/convex-snek-platform/` whose type structurally cannot carry the email, route every user-facing query, subscription and exported record shape through it — the field absent from the shape, never returned and hidden — and add a mechanised guard (test or type-level assertion over the exported shapes) so a *new* view built on the same shape cannot leak either (`accounts-and-profiles/email-confidentiality#omitted-at-the-boundary`, `#hidden-even-from-self-view`)
- [ ] 3.2 Confine email reads to the identity-matching and administrative paths that need them, and add no user-facing surface exposing an email — including for platform admins, since this delta mints no such view (`accounts-and-profiles/email-confidentiality`)
- [ ] 3.3 Enforce email-free participation snapshots: the per-game snapshot stores user references only, and display names resolve through the email-free projection. The snapshot record is `game-lifecycle/roster-snapshot`'s — land this as a shape constraint plus a regression test over its validator, not as a second owner of the snapshot (`accounts-and-profiles/email-confidentiality#participation-snapshots-are-email-free`)
- [ ] 3.4 Gate every query behind this capability at the Convex function contract in `packages/convex-host/`, never in the app's routing, so an unauthenticated visitor can reach, index or enumerate none of it and a fork cannot open it; the authentication requirement itself is `identity-and-authorization/authentication-required`'s (`accounts-and-profiles/no-public-surface#unauthenticated-visitors-see-nothing`)
- [ ] 3.5 Impose no second gate among authenticated users on any profile, statistic, history or leaderboard read — membership, role and standing scope discovery only — and keep the reference app's unauthenticated route exemption list to sign-in, sign-out and static assets, matching the empty public carve-out (`accounts-and-profiles/no-public-surface#authenticated-users-face-no-further-gate`)

## 4. Snapshot attribution, history listings and aggregate statistics (Convex query layer)

- [ ] 4.1 Build the historical-presentation query layer so every listed participant, opponent, result and score resolves from the game's participating-team snapshot and the recorded outcome, with no read of current team or membership records on any historical path, and so archiving is inert for presentation — an archived team or opponent renders under its historical identity with nothing recomputed (`accounts-and-profiles/snapshot-attribution#team-of-the-day`, `#roster-changes-rewrite-nothing`, `#head-to-head-archive-stable`)
- [ ] 4.2 Implement one shared, scope-parameterised listing query serving the player profile, the team profile and `replay-and-audit`'s per-hosted-team history page, and compute each profile's aggregate statistics from exactly that query's result set rather than recomputing independently — so the eligibility rule, the normalised-score headline and the statistics/listing agreement exist once and cannot drift between surfaces (`accounts-and-profiles/player-profile#history-outlives-membership`, `accounts-and-profiles/aggregate-statistics#consistent-with-the-listing`, seam: `replay-and-audit/team-game-history`)
- [ ] 4.3 Produce the required aggregates — player: games played, win rate, average team score; team: games played, win rate, average score, head-to-head against every distinct opponent with none omitted — all on the normalised score (`accounts-and-profiles/aggregate-statistics`)
- [ ] 4.4 Compute head-to-head pairwise: a game with N competing teams contributes N−1 entries per participant, each settled by comparing just those two teams' final scores in that game and never by who won the game overall — so an opponent met only in three- and four-team games is still recorded, and a team may hold a winning record against a team that placed above it. Test the two-team case and a four-team case together so the general rule is what ships (`accounts-and-profiles/aggregate-statistics#pairwise-inside-a-multi-team-game`, `#head-to-head-covers-every-opponent`, seam: `game-engine/scoring`)
- [ ] 4.5 Implement the presented-game predicate once, in the shared listing query of §4.2, so every history, statistic, head-to-head and ranking is drawn from the same set: finished games carrying a recorded outcome. A game finished by failure with no scores recorded is excluded from listing and aggregate identically; a game decided without play but carrying an outcome is included. Test that the exclusion cannot be applied on one side only (`accounts-and-profiles/recorded-outcomes-only#a-failed-game-counts-nowhere`, `#decided-without-play-still-counts`, `accounts-and-profiles/aggregate-statistics#consistent-with-the-listing`, seam: `game-lifecycle/finish-notification#error-outcome-still-finishes`)

## 5. Leaderboard (Convex query layer)

- [ ] 5.1 Model the ranking criteria and time windows as exhaustive closed unions — win rate with a qualifying threshold, total wins, average normalised score; all time, last 30 days, last 7 days — so adding one is a compile error until the requirement is revised, and implement criterion switching and window filtering over the snapshot-resolved game set. Close the *criterion* and *window* unions only: leave a ranked entry's rendered content open to extension, so a downstream capability requiring an annotation on an entry needs no revision here (`accounts-and-profiles/leaderboard#closed-sets-only`)
- [ ] 5.2 Implement the optional single-room restriction such that every criterion and window is recomputed over that subset alone, never filtered after ranking (`accounts-and-profiles/leaderboard#room-scoped-ranking`)
- [ ] 5.3 Keep archived teams in the default ranking under their archived identity with nothing recomputed, and verify no other team's standing shifts when a rival archives (`accounts-and-profiles/leaderboard#archived-teams-still-ranked`)
- [ ] 5.4 Feed forfeited games into every criterion as games the team played, taking the score from the one shared scoring implementation rather than special-casing a value here — games played, the qualifying threshold, win rate and average score all include them. Test that a team's standing does not improve by forfeiting rather than losing. Scope: the ranking treatment only — *labelling* a forfeited game as a forfeit on an entry, a profile history or any other presentation is required by `tournaments/forfeit-scoring#forfeit-visible-downstream` and arrives as a diff to these surfaces authored with that capability; this change neither implements nor restates it (`accounts-and-profiles/leaderboard#forfeits-rank-rather-than-vanish`, seam: `game-engine/scoring#forfeit-exclusion`)
- [ ] 5.5 Choose the minimum-games qualifying threshold value and record it as a tuning parameter with a `// design:` reference to this change — its existence is spec, its value deliberately is not (`accounts-and-profiles/leaderboard`)

## 6. Web surfaces (apps/centaur-server-reference)

- [ ] 6.1 Establish the platform-scoped route shell and persistent global navigation reaching home, the teams browser, the viewer's own profile and the leaderboard, then build the home view on it: the user's current teams, recently visited rooms, and the in-progress games of the user's own teams, every entry a direct link — including the cross-server link to a team's live surface. The nav shell has no requirement home of its own (it is mechanism serving each surface's owner), and the recently-visited-rooms memory shape is plastic (`accounts-and-profiles/home-view#live-participation-surfaces`, `#home-links-onward`)
- [ ] 6.2 Build the teams browser: name, display colour and current captain per team, archived teams absent from the default listing while their profiles stay reachable, every entry opening the team profile (`accounts-and-profiles/teams-browser#entry-opens-the-profile`, `#archived-hidden-not-gone`)
- [ ] 6.3 Build the player profile view for every user record — reachable from global navigation for oneself and linked from member listings and game histories — showing display name, memberships, and the snapshot-scoped chronological history with room, date, participating teams, result and scores (`accounts-and-profiles/player-profile#every-user-has-one`, `#history-outlives-membership`)
- [ ] 6.4 Derive the profile's "teams played for" from the participating-team snapshots of the games in the user's own history — no membership-history record is created here or asked of `team-management`, and `team-management/roster-of-operators` stays current-membership-only with no soft-deleted rows standing in for history. Test the accepted limitation explicitly so nobody later "fixes" it: a user who joined and left a team with no game played in between shows that team nowhere once gone (`accounts-and-profiles/player-profile#past-teams-are-teams-played-for`, seam: `game-lifecycle/roster-snapshot`)
- [ ] 6.5 Build the team profile view for every team, archived included: identity, current roster, captain, server nomination with latest recorded health status, full chronological history and statistics, with no mutating affordance — at most a link onward to the management surface where authority is enforced (`accounts-and-profiles/team-profile#full-history-for-any-viewer`, `#strictly-informational`, `#archived-teams-keep-their-profile`)
- [ ] 6.6 Build the leaderboard view with criterion and window controls, the optional room restriction, and each ranked entry linking to its team profile (`accounts-and-profiles/leaderboard`)
