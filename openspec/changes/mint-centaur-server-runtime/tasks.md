# mint-centaur-server-runtime — Tasks

## 1. Pre-implementation & seam gates

- [ ] 1.1 Review this change's artifacts with the author immediately before implementation begins, and refine this task breakdown then; resolve Q-A (`whitelist-admission`), Q-B (`reference-server-home`) and Q-C (the mirror workflow's disposition) first. Only a reversal changes this plan — Q-A or Q-B reversed adds a requirement and its tasks here, and §6 already assumes Q-C's recommended answer
- [ ] 1.2 Seam gate — capabilities that must be implemented or agreed first, and which archive before this change: `application-shell` (the one application this server serves and delivers as a fork) and `global-invariants` (the trust-chain rules key publication and the administration API rest on)
- [ ] 1.3 Confirm the runtime home this plan assumes: every requirement here is realised in the Snek Centaur Server deployment — `packages/centaur-server-lib` and `apps/centaur-server-reference` — with no Convex function code and no SpacetimeDB module code in scope. **Those two packages are not this capability's to own.** `team-server-management` builds server-side code in them too — outward authentication, answering an invitation from the whitelist, the shared-hosting route families — and the hosting session running inside this same process is `bot-framework`'s. The boundary is the requirement, never the directory (`team-server-management/invitation-acceptance`, `team-server-management/shared-hosting`, `bot-framework/embedded-team-player`)
- [ ] 1.4 The three platform-facing paths are settled and fixed platform-wide — `POST /.well-known/snek-game-invite`, `GET /.well-known/snek-server-keys`, `GET /.well-known/snek-healthcheck`. Build against exactly these, exported from the library as the single constant every implementation reads (`centaur-server-runtime/forkable-reference-app#enumerated-surface-is-the-contract`, `centaur-server-runtime/healthcheck-endpoint`, `centaur-server-runtime/server-key-publication`)
- [ ] 1.5 Keep the retired spellings out: the scaffold's root `/healthcheck` (legacy module 02's Design) and `/.well-known/jwks.json` (renamed because the platform's own OIDC surface already serves a document at that relative path, with different trust semantics). `apps/` and `packages/` are already on the new spellings, so this is a guard on new code and on the mirror output rather than a hunt; occurrences in `legacy-spec-archive/` and in the two changes' design prose are historical and deliberate and must not be swept (`centaur-server-runtime/forkable-reference-app#surface-changes-are-platform-changes`)
- [ ] 1.6 File provisional IANA registrations for the three well-known suffixes under RFC 8615 §3.1, which requires registration of any minted well-known URI. Not a blocker for implementation — unregistered use is a deviation taken knowingly and bounded by the `snek-` prefix — but the protocol does require third parties to serve these paths (`centaur-server-runtime/forkable-reference-app`)

## 2. Self-provisioning identity

- [ ] 2.1 Generate a signing keypair on first start if none is persisted, persist it, and publish the public half at the well-known keys path — no operator action, nothing to copy, paste or register. The key store belongs in the library so every fork inherits it; the app's route only serves what the library holds (`centaur-server-runtime/server-key-publication`, `#first-boot-needs-no-operator`)
- [ ] 2.2 Support publishing several keys at once so rotation is publish-both, switch, drop-the-old with no exchange with the platform, and test that a redeploy onto storage that lost the key regenerates, republishes, and resumes. The requirement's fallback — the platform authenticating servers by a challenge it initiates, should invisible provisioning prove impossible — is platform-side work this change may not take on its own; escalate rather than implement it (`centaur-server-runtime/server-key-publication#rotation-is-uncoordinated`, `#ephemeral-storage-self-heals`)

## 3. Liveness

- [ ] 3.1 Implement the healthcheck endpoint: unauthenticated, minimal, liveness only, answering identically whether or not the deployment operates any team; test that it carries no team-scoped state and that a server with an empty whitelist answers exactly as a loaded one does (`centaur-server-runtime/healthcheck-endpoint`, `#unauthenticated-and-minimal`, `#liveness-is-not-readiness-to-play`)
- [ ] 3.2 Keep `HealthcheckResponse` reduced to `status` and `version` — it has already been narrowed to those two — and pin it with a test, since extending it with hosted-team or active-game counts is a violation of the contract rather than an enrichment of it (`centaur-server-runtime/healthcheck-endpoint#unauthenticated-and-minimal`)

## 4. Administration

- [ ] 4.1 Implement the administration API over a local set of trusted administrative issuers, each recorded with its capability ceiling, enforcing exactly what a presented credential carries and refusing anything beyond the issuer's ceiling at the resource. That set is this deployment's own configuration: the server is a second resource holder under the same invariant, never a reader of the platform's registry (`identity-and-authorization/trusted-issuer-registry`) (`centaur-server-runtime/server-administration-api`, `#an-issuer-may-mint-narrower-than-itself`, `#capabilities-beyond-the-ceiling-are-refused`)
- [ ] 4.2 Negative space — the administration API is deliberately **not** in the enumerated compatibility surface. No fourth well-known path is minted for it: it lives in the fork's own path space, its routes are not fixed platform-wide, and a fork may restructure them freely (`centaur-server-runtime/forkable-reference-app#the-rest-of-the-path-space-is-the-forks`)
- [ ] 4.3 Make admit and remove idempotent, and test that the platform is not called, consulted, or informed anywhere in this path (`centaur-server-runtime/server-administration-api#adding-an-already-whitelisted-team-succeeds`, `#the-platform-is-not-in-this-path`)
- [ ] 4.4 Make the capability set extensible without a protocol change, and test that adding one needs no configuration change on a deployed server (`centaur-server-runtime/server-administration-api`)

## 5. Tenancy and identity posture

- [ ] 5.1 Make the library's connection management per team and per game throughout, with no ambient client standing in for all hosted teams, and test that a server operating three teams holds three separate credential and subscription sets. Seam: the per-team player that consumes this — one per hosted team per live game — is `bot-framework`'s and is not built here (`centaur-server-runtime/library-tenant-separation`, `#no-ambient-client`, `bot-framework/embedded-team-player`)
- [ ] 5.2 Hold no user record, no session, and no identity state of any kind, and authenticate no person: add a test that the deployment registers no identity-provider client and exposes no sign-in route, and one that serving the application to a visitor with no relationship to the operated teams exposes nothing — because there is nothing to expose (`centaur-server-runtime/no-operator-state`, `#no-per-server-sign-in`, `#serving-the-wrong-visitor-exposes-nothing`)
- [ ] 5.3 Restrict the reference implementation to reference-distributed heuristics whenever it operates more than one team, with the single-tenant case unrestricted. The restriction binds the reference deployment alone — nothing on the platform constrains a third-party operator who runs team-supplied code, and nothing is built to. Seam: what a heuristic implementation *is*, and where the registry naming them lives, is `bot-configuration`'s, whose task 1.4 is still choosing between an in-app registry, a library-exported one, and widening the mirror prefix — that choice binds §6.1 (`centaur-server-runtime/reference-heuristics-on-shared-hosting`, `#shared-reference-server-refuses-team-code`, `#single-tenant-server-runs-anything`, `#other-operators-choose-for-themselves`, `bot-configuration/registry-defines-availability`)

## 6. Distribution — the fork and the library

- [ ] 6.1 Build the mirror publishing path as **mechanism**: `.github/workflows/mirror-centaur-server.yml` (it does not exist, though root `AGENTS.md`, `apps/centaur-server-reference/AGENTS.md` and `docs/external-setup.md` all describe it as though it did), the `git subtree split --prefix=apps/centaur-server-reference` it runs, and the dependency rewrite in the split output. Correct those three documents to what is actually built. The prefix is a decision, not a given — see the seam in task 5.3
- [ ] 6.2 **Unresolved — settle before the rewrite is written:** what a fork actually resolves the library from. The repo records three incompatible answers: both `AGENTS.md` files and `docs/external-setup.md` say `github:cyphid/snek-centaur-server-lib#<tag>`, but nothing ever creates that repository; tags are cut as `centaur-server-lib@v<semver>` on the monorepo; npm is filed as a future upgrade path. A git-ref install additionally needs built output the package does not carry, since `exports` points into a gitignored `dist/`. Choose one channel and make every document say it (`centaur-server-runtime/published-library-surface`)
- [ ] 6.3 Publish the library as a versioned artifact — it is at `0.0.0` today — and define its published interfaces as a single entry point rather than deep paths, so the compatibility surface is enumerable. This is a transitive problem, not a one-line rewrite: the library itself depends on `@cyphid/snek-engine` (today `private: true`), `@cyphid/convex-snek-platform` and `@cyphid/convex-centaur-state`, all `workspace:*`, and a fork must consume the same engine build rather than a copy of it. Rewriting only the app's dependency on the library leaves a fork unable to install. What the surface *contains* is co-owned — the heuristic vocabulary is `bot-framework`'s, the invitation handler and whitelist types `team-server-management`'s; this capability owns only the discipline that keeps it stable (`centaur-server-runtime/published-library-surface`, `global-invariants/one-shared-engine#no-parallel-implementation`)
- [ ] 6.4 Prove the fork story end to end: clone the mirror output into a clean directory with no access to this repository, install, build, and run it; the test fails if any dependency resolves through the workspace (`centaur-server-runtime/published-library-surface#a-fork-builds-without-the-monorepo`)
- [ ] 6.5 Adopt and document a release discipline in which removing or narrowing a published interface is a breaking version, and test the pinning: publishing a newer version leaves a fork pinned to an earlier one still building and still being operated (`centaur-server-runtime/published-library-surface#pinned-forks-do-not-drift`, `#a-removal-is-a-version-not-a-surprise`)
- [ ] 6.6 Surface-change discipline, which the paths make mechanical: assert the library's exported path constant against the reference app's route tree and that the app serves no platform-facing route outside `/.well-known/snek-`, so drift cannot be discovered by a fork when its invitations stop arriving; and test that a fork restructuring every other route — a status page at the root, a differently organised admin area — stays platform-compatible (`centaur-server-runtime/forkable-reference-app#surface-changes-are-platform-changes`, `#enumerated-surface-is-the-contract`, `#the-rest-of-the-path-space-is-the-forks`)
- [ ] 6.7 Publish the enumerated compatibility surface as one durable artifact carried into the mirror — the three paths, the published library interfaces the application consumes, and the converse a forker most needs to read: that nothing outside the prefix binds them (`centaur-server-runtime/forkable-reference-app#enumerated-surface-is-the-contract`, `#the-rest-of-the-path-space-is-the-forks`)
