- [ ] 1.1 Review this change's artifacts with the author immediately before implementation begins, and refine this task breakdown then

- [ ] 1.3 Agree with `migrate-team-server-management` the two contract shapes this capability branches on but does not own — the reciprocal of that change's own seam task: the per-team invitation resolution set (accepted / declined / no answer within the window) together with the naming an abort reports, and the per-team recorded health status a manual start reads. Open Question 1's resolution (ten seconds) is already carried by the sibling's own requirement — verified present at planning time — and this change deliberately restates no number (team-server-management/game-invitations, team-server-management/invitation-acceptance, team-server-management/server-healthcheck, game-lifecycle/launch-gates#refusal-aborts-cleanly)
- [ ] 1.4 Obtain an author decision on who owns the self-hosted SpacetimeDB provisioning host as a deliverable: its deployment, its management API, its scale-to-zero hosting model, and the WASM-binary storage the provisioning call draws from are all code-mechanism assigned to no capability, yet neither the instance bracket nor the warm-up signal can be implemented without them (game-lifecycle/instance-per-game, game-lifecycle/host-warm-up)
- [ ] 1.5 Install and wire the runtime toolchains this change is the first to need. Convex: the SDK in `packages/convex-snek-platform/` and `packages/convex-host/` (both are SDK-free typed stubs today, with `schema.ts` and `convex.config.ts` placeholders). SpacetimeDB: this change is the first consumer of the module, so it owns standing the toolchain up to the depth it needs — how `packages/stdb` builds into a deployable module artifact, which SDK/host version is pinned, and a smoke harness that can run one reducer — and records the setup durably in `packages/stdb/AGENTS.md` and, for anything beyond a plain install, the committed session-start hook. **Seam:** the deepening — generated client bindings for every consumer, the reducer test harness that drives two invocations into one transaction window, and the record-to-record determinism harness — is `mint-game-runtime`'s, which folds after this change

## 2. Convex game record, status machine, roster snapshot, and the published engagement fact (`packages/convex-snek-platform`, mounted by `packages/convex-host`)

- [ ] 2.1 Replace the `schema.ts` placeholder with the real `games` table and align the `GameRecord` type in `src/index.ts`: status, frozen configuration, instance reference, the `playing` and `finished` timestamps, the final outcome, and the unseated-teams field; teardown clears only the instance reference, so outcome, timestamps and seating history survive indefinitely. Shape the outcome field so a finished game carrying a result is distinguishable from one finished by failure carrying none: `accounts-and-profiles/recorded-outcomes-only` filters every history, statistic and ranking on exactly that distinction, and a walkover or no-contest carries a result while an error finish must not read as one. Sweep all three runtimes for surviving `ended`/`endedAt` vocabulary first — `GameStatus` and `finishedAt` are already aligned to the delta, so this is a verification pass, not a rename (game-lifecycle/game-record, #record-outlives-the-instance)
- [ ] 2.2 Record-first discipline across every lifecycle entry point: each takes an existing game id, and no path provisions an instance, delivers an invitation, initializes, handles a finish, or creates a successor for a game with no record (game-lifecycle/game-record#record-precedes-everything, game-lifecycle/no-orphans#record-always-first)
- [ ] 2.3 Single Convex transition helper as the sole writer of status, enforcing the closed three-transition set inside its own mutation transaction — `not-started → playing`, `playing → finished`, and the direct walkover — refusing every backward and every out-of-set move; no `playing` write outside the orchestration's terminal success step and no `finished` write outside terminal handling, so an aborted launch is structurally incapable of being observed as `playing` (game-lifecycle/status-authority, #no-backward-motion, #walkover-straight-to-finished, #aborted-launch-was-never-playing)
- [ ] 2.4 Append-only per-game roster snapshot written at initialization holding exactly the seated teams with their authorized members, with no update or delete path and — deliberately — no per-member role field of any kind, since `team-management/roster-of-operators` leaves nothing to populate one with; every per-game membership read resolves against the snapshot rather than the live team records (game-lifecycle/roster-snapshot, #snapshot-survives-later-edits, #restricted-set-is-what-binds)
- [ ] 2.5 Publish the competitive-engagement fact as a team-addressed read: derived once here from the team's participation snapshots and its games' statuses, true from a game's commit to `playing` until that game is `finished`, held open while *any* of the team's games is still in play, and evaluated inside the transaction of a write that must be refused while it holds. Give it exactly one implementation and one call shape, and add a regression check that no capability outside this one joins game status to participation to answer the same question for itself — the inverted dependency edge only pays off if consumers consume (game-lifecycle/competitive-engagement, #published-not-inferred, #engaged-while-any-of-its-games-plays, #a-game-that-never-played-engages-nobody). Seam: there are two consumers, not one — `team-management/roster-freeze` reads it while declaring no dependency on this capability by design, and `rooms-and-matchmaking/room-mode` reads it (over the edge it already declares) to license the one enrolment change a playing room admits; one call shape must serve both, evaluable inside each caller's own write transaction. `tournaments/tournament-roster-freeze` is a separate freeze source anchored to its own state, not to this fact

## 3. Per-game instance bracket and the provisioning host (SpacetimeDB provisioning host + Convex actions in `packages/convex-host`)

- [ ] 3.1 Stand up the self-hosted SpacetimeDB provisioning host and its management API — create and delete a per-game database from the platform's stored WASM module, under a suspend-when-idle hosting model. Greenfield infrastructure with no code, no config, and no owning package in the repo today; blocked on 1.4 (game-lifecycle/instance-per-game)
- [ ] 3.2 The provisioning authority model, which is the security half of 3.1 and is what makes an unauthenticated creation route safe to stand up: the platform signs its own credential at the moment of each call and stores no credential specific to the provisioning system, ownership is what protects an instance that already exists, and the creation route — which the host itself admits without authorization — is closed at the network boundary to callers bearing a valid platform-issued credential. The credential check is what carries the guarantee; narrowing by network origin is defence in depth on top of it, never the thing relied upon. Test all three, since none of them fails visibly when it is missing (game-lifecycle/instance-provisioning-authority, `#no-provisioning-credential-is-stored`, `#only-the-provisioner-can-touch-an-instance`, `#open-creation-is-closed-at-the-boundary`)
- [ ] 3.3 Convex provision and teardown actions authenticated as the platform against that management API, as the only callers of either operation; provisioning is reachable only from launch orchestration and never from record creation, and every launch path — a setting's first game, an auto-created successor, a scheduled round — gets a newly provisioned instance with no reuse or recycling (game-lifecycle/instance-per-game, #no-instance-before-launch, #fresh-on-every-path, game-lifecycle/launch-orchestration#privileged-operations-are-platform-only)
- [ ] 3.4 Orphan cleanup on every post-provisioning failure path of the orchestration — payload rejection, invitation abort, unexpected error — tearing the just-provisioned instance down before the game is left `not-started` (game-lifecycle/no-orphans, #post-provisioning-failure-cleans-up)
- [ ] 3.5 Warm-up signal on the provisioning host, distinct from provisioning: ready-or-no-op success within ten seconds, satisfied by a lightweight check rather than the platform-management credential, provisioning nothing and mutating no existing instance (game-lifecycle/host-warm-up, #warm-signal-is-idempotent)
- [ ] 3.6 Best-effort Convex warm-up dispatch scheduled after every game-record-creating transaction commits, decoupled from the creation: at most one retry, failure and timeout swallowed, never surfaced to the acting user, never blocking or rolling back creation, with the scheduling primitive left plastic in code (game-lifecycle/host-warm-up#warm-up-never-blocks-creation, #cold-start-fallback)

## 4. Launch orchestration and gates (Convex action, `packages/convex-host`)

- [ ] 4.1 The single Convex-orchestrated launch action implementing the ordering the requirement fixes — freeze configuration, obtain the starting state, provision, deliver invitations and await resolution, initialize with the restricted roster, commit `playing` — with every privileged step authenticated as the platform and no non-platform caller path to provisioning, initialization, callback registration or teardown; step numbering, endpoint paths, payload field lists and management-API mechanics stay in code (game-lifecycle/launch-orchestration, #privileged-operations-are-platform-only). **Seam:** the status stays `not-started` for the whole orchestration, so a launch in flight is invisible in the status machine — yet `rooms-and-matchmaking/room-mode` derives a room's playing mode from its current game and stores no flag of its own, and so needs an observable "a launch of this game is under way" that only this capability can expose. Agree its shape with `migrate-rooms-and-matchmaking`, together with where that change's initiation gate hands off to this action (rooms-and-matchmaking/room-mode#the-mode-is-never-a-stored-flag, rooms-and-matchmaking/game-start-gate)
- [ ] 4.2 Starting state obtained before any provisioning call, from the locked-in preview or a fresh generation, with generation failure halting the launch and surfacing `game-configuration`'s structured infeasibility to the configuring user with nothing provisioned (game-lifecycle/launch-orchestration#generation-failure-provisions-nothing)
- [ ] 4.3 Invitation-resolution barrier: initialization is unreachable until every invitation has been accepted, refused or timed out, and the roster handed to initialization is exactly the seated set, so no snake is ever spawned for a non-participating team (game-lifecycle/launch-orchestration#invitations-resolve-before-init)
- [ ] 4.4 Manual-start gates: block the launch while any participating team's nominated server reports unhealthy — naming the failing teams' servers to the starting user and re-permitting the start once all pass — and abort on refusal or timeout with the instance torn down, the game still `not-started`, and an error on the record naming the declining or unresponsive servers. Settle and record where the health gate sits relative to provisioning: the delta's ordering list omits it deliberately, so the placement is a code decision that must keep a doomed manual start from provisioning at all. Settle staleness too — the sibling records health on demand and is under no obligation to poll, so the recorded value can be arbitrarily old; decide whether the gate triggers a fresh check, which that requirement expressly sanctions for a platform surface, or blocks on the recorded status and its timestamp (game-lifecycle/launch-gates, #unhealthy-server-blocks-manual-start, #refusal-aborts-cleanly, team-server-management/server-healthcheck#on-demand-not-polled, #member-triggered-check)
- [ ] 4.5 The override branch as an abstract capability of the orchestration — recorded health ignored, a refusal or timeout costing that team its seat instead of aborting, and a fall to the walkover below the minimum needed to play — expressed without reaching for competition-format vocabulary; the schedule-bound caller that exercises it belongs to `tournaments` (game-lifecycle/launch-gates#override-seats-the-willing, game-lifecycle/status-authority#walkover-straight-to-finished)

## 5. Instance initialization and fresh per-game state (`packages/stdb` reducer + the Convex launch-time state hook)

- [ ] 5.1 Real `initialize_game` reducer replacing the stub in `packages/stdb/src/index.ts`: privileged, platform-authenticated, with a re-invocation guard evaluated inside the write's own transaction so a second invocation is rejected with the instance's state untouched; successful initialization leaves turn 0 fully written and the instance ready for connections, staging and turn declarations (game-lifecycle/instance-initialization, #initialization-is-once-only)
- [ ] 5.2 Initialization payload contract and its structural validation: precomputed starting state, dynamic gameplay parameters, the game's root seed always forwarded, the roster snapshot seeding admission, the game identifier for validating access-token audience, and the finish-notification callback registration — the instance never generates a board, and a structurally invalid payload is rejected synchronously to the caller without initializing so the orchestration's cleanup path runs (game-lifecycle/instance-initialization, #malformed-payload-rejected, game-lifecycle/roster-snapshot)
- [ ] 5.3 Pre-initialization closure in the instance: client connections refused and disconnected, gameplay operations rejected, and no game clock running until initialization completes — the game's playable life begins strictly after it (game-lifecycle/instance-initialization#nothing-before-init)
- [ ] 5.4 Convex-side per-game platform state initialization during launch for each seated team: idempotent so an orchestration retry is a harmless no-op with no duplicate records and no reset, and keyed by exactly the snake identifiers the delivered starting state carries. Cover the negative half with a successor-path test proving no per-game platform record of any kind exists before the successor's own launch creates it (game-lifecycle/fresh-game-state, #idempotent-initialization, #identifiers-agree, #successor-inherits-config-not-state). **Seam:** what those records contain is not this capability's — `bot-configuration/game-start-snapshot` captures the team's defaults into game-scoped values and `operator-control/exclusive-selection` opens the selection rows, both living in `packages/convex-centaur-state`. This change owns the hook (once per seated team, at launch, idempotent, keyed by the generated snake identifiers) and the negative that nothing per-game exists before it runs; it authors none of the record shapes, which is why the delta enumerates no state kinds

## 6. Game end: commit boundary, notification, teardown, successor (`packages/stdb` + Convex HTTP action)

- [ ] 6.1 Fix the end of a game at the resolving commit and nowhere else: the commit of the turn whose resolution detects an end condition is the single event that establishes the game as over, and every step of terminal handling — notification, persistence, the transition to `finished`, teardown — is downstream of it, with nothing outside the game's own runtime deciding it and no sweep or observation anticipating it (game-lifecycle/game-end-boundary, game-lifecycle/game-end-boundary#the-commit-is-the-end, game-lifecycle/game-end-boundary#terminal-handling-follows-the-commit). **Seam:** what the instance refuses from that commit onward is `game-runtime/game-over-freeze`'s
- [ ] 6.2 Terminal notification pushed from the instance to the callback registered at initialization, carrying the outcome together with the complete game record, presenting the pre-signed credential unchanged — the instance mints, signs and derives nothing — with delivery retried a bounded number of times and the retry count and backoff schedule left plastic in code behind a `// design:` reference (game-lifecycle/finish-notification)
- [ ] 6.3 Convex game-end HTTP action: validate the presented credential as a self-contained proof — verified, never compared against a stored copy, never persisted — refusing a credential that does not validate as platform-issued for this game without touching status; then record the outcome, persist the record, transition to `finished` and tear down, with an error outcome still finishing and still tearing down but recording no scores (game-lifecycle/finish-notification#forged-callback-refused, #error-outcome-still-finishes)
- [ ] 6.4 Scheduled stale-game sweep in Convex over records still marked `playing` for which no finish notification has arrived, selecting on elapsed time past a bound set comfortably above the maximum wall-clock duration the game's frozen clocks and turn limit can produce — never above an observed typical game. That maximum is always available: `game-configuration/bounded-game-duration#launch-cannot-freeze-an-unbounded-game` refuses to freeze a configuration carrying neither a turn limit nor a duration limit, so no launched game is unbounded and every record's own configuration yields a finite figure. Whether the bound is derived per game or fixed as one constant above the worst admissible configuration is open; either way record the derivation beside the value behind a `// design:` reference, since the value is plastic and the property it must have is not. The sweep cadence is likewise plastic (game-lifecycle/stale-game-recovery, #stale-only-past-the-maximum-game-duration, game-lifecycle/finish-notification#lost-notification-recovered, #pushed-never-polled-live)
- [ ] 6.5 Liveness probe against the instance behind a stale record, reachable only from the sweep and only for a record already past the bound: it answers whether a live instance stands there and reads nothing about the game — no turn log, no staged moves, no board — so recovery adds no channel for observing a game in progress. Keep it a distinct call from the record retrieval, and add a test asserting the probe path touches no gameplay-bearing table (game-lifecycle/stale-game-recovery#probing-is-not-licence-to-watch-a-game, game-lifecycle/finish-notification#pushed-never-polled-live)
- [ ] 6.6 Live-instance recovery branch: retrieve the completed game record from the answering instance over `replay-and-audit/once-at-end-export`'s platform-only retrieval rather than a second egress channel invented for recovery, and hand it to the *same* terminal handling the pushed notification uses — persist, transition to `finished`, tear down, in that order — rather than a parallel implementation, so the persistence gate binds identically on both paths; a retrieval yielding no completed record leaves the status untouched for a later sweep, and the transition commits under the same guard as the pushed path so a late-arriving notification cannot finish the game twice (game-lifecycle/stale-game-recovery, #live-instance-yields-the-record, game-lifecycle/teardown-after-persistence#no-teardown-before-persistence)
- [ ] 6.7 Dead-instance recovery branch: when the probe finds no live instance — reaped, crashed or unreachable — take the game to `finished` with an error outcome recording no scores, and reclaim whatever of the instance remains. Assert in a test that the persistence gate is satisfied vacuously here rather than bypassed: reclamation runs only when no record can be retrieved, and the identical reclamation call is refused for an instance that does hold one (game-lifecycle/stale-game-recovery, #vanished-instance-finishes-with-an-error, #nothing-left-to-persist-when-the-instance-is-gone, game-lifecycle/finish-notification#error-outcome-still-finishes)
- [ ] 6.8 Teardown gate: no teardown until Convex has confirmed persistence of the complete record, the instance staying available and discarding nothing not yet retrieved until then so persistence can be retried against it; teardown immediately in the same terminal handling once confirmed; and no self-teardown capability anywhere in the instance, not even after acknowledgement (game-lifecycle/teardown-after-persistence, #no-teardown-before-persistence, #no-self-teardown, #prompt-after-confirmation)
- [ ] 6.9 Successor auto-creation as one Convex transaction that creates the new `not-started`, mutable, instance-less record inheriting the predecessor's configuration values with a clear preview lock and no persisted preview carried over, and installs it as the current game in the finished game's setting — immediate by default, and the same code path when a competition format governs when (or whether) the next one is created. Include a concurrency test proving concurrent finish handling can produce neither two successors nor an interval with none designated (game-lifecycle/successor-auto-creation, #atomic-with-currency, #mutable-again, #no-preview-carried)
