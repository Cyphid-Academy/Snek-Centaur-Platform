## 2. Room record and platform read surface (Convex — `packages/convex-snek-platform`)

- [ ] 2.1 Define the `rooms` table and its indexes in `packages/convex-snek-platform/schema.ts`, replacing the placeholder: name, optional owner, current-game reference, enrolled-team set, archived flag — and deliberately **no** configuration and **no** readiness fields, both of which live on the current game's record (rooms-and-matchmaking/room-record, room-record#no-parameter-state-on-the-room)
- [ ] 2.2 Room read surface: reactive queries backing the browser and the lobby — listing (archived excluded by default, name search) and single-room read resolving owner-or-ownerless state, enrolled teams, and the current game's own configuration and readiness from the game record. The "is being played" indicator reads game status, owned by game-lifecycle/status-authority (rooms-and-matchmaking/room-record, room-discovery, room-lobby)
- [ ] 2.3 Derive the room's mode — configuring or playing — from the room's current game and store no mode flag on the room record: one exported predicate every guard and every surface reads, true from the moment a launch of the current game begins until the room's current game is once again one awaiting launch, so an aborted launch reads as configuring and a finished game's successor installation flips the room back in the same transaction (rooms-and-matchmaking/room-mode, room-mode#the-mode-is-never-a-stored-flag, room-mode#configuring-resumes-with-the-successor, room-record#no-parameter-state-on-the-room). The status values it reads are game-lifecycle/status-authority's and the "launch under way" signal is game-lifecycle/launch-orchestration's — agree with `migrate-game-lifecycle` how the in-flight-launch state is observable, since the status stays `not-started` for the whole orchestration
- [ ] 2.4 Currency test across the succession seam: an integration test asserting the room's current-game reference designates the auto-created successor and the finished game stays reachable as history (rooms-and-matchmaking/room-record#currency-moves-with-the-succession). The atomic install of the successor as current is game-lifecycle/successor-auto-creation#atomic-with-currency — implemented there, only observed here

## 3. Room lifecycle mutations: creation, administration, archival (Convex — `packages/convex-snek-platform`, auth wrappers in `packages/convex-host`)

- [ ] 3.1 `createRoom` as one transaction: the room record with the creating user as owner, plus its initial not-started game with default parameter values and no team ready, installed as the room's current game in the same act (rooms-and-matchmaking/room-creation, room-creation#born-with-a-game, room-creation#creator-owns-from-the-first-instant). The game record's shape and its defaults belong to game-lifecycle/game-record and game-configuration; this path also triggers game-lifecycle/host-warm-up's best-effort dispatch rather than re-implementing it
- [ ] 3.2 One shared administrative-actor guard — owner, or any authenticated caller with access when the room is ownerless — applied by every administrative mutation (enrolment change, configuration edit, start, abdication, archival), evaluated inside each mutation's own transaction (rooms-and-matchmaking/room-administration, room-administration#ownerless-means-open-control, room-administration#non-actor-rejected-at-the-function). Configuration editing itself is game-configuration's work; only the authority check is this capability's
- [ ] 3.3 The governing-format arm of the same guard: while a competition format governs the room, enrolment changes, starting the current game, and archival are refused to every user including the owner, while configuration and abdication stay open — with the room otherwise indistinguishable from a user-created one (rooms-and-matchmaking/room-administration#reserved-acts-belong-to-the-governing-format, room-creation#a-formats-room-is-an-ordinary-room). Which format governs a room, and how it acts on it, is the format's own capability's work; only the refusal is this capability's
- [ ] 3.4 `abdicateOwnership`: sets the room ownerless irreversibly, with a negative test that no code path anywhere assigns a room's owner after creation — there is no claim, grant, or transfer mutation to write (rooms-and-matchmaking/room-administration#abdication-is-forever)
- [ ] 3.5 `archiveRoom` / `unarchiveRoom` with no deletion path existing at all: archival rejected while the room is playing — the same mode predicate of 2.3 the enrolment gate of 4.2 uses, so the two bars cannot disagree — **and** at any moment a competition format governs the room, the second test being the one that matters between a format's contests, when the room is configuring and the bar must hold anyway — archived rooms excluded from default listings, no game created or started while archived (the guard sitting with the creation mutation of 3.1 and the start gate of section 4, in-transaction), and nothing stripped by the round trip: enrolment, ownership state and current game intact (rooms-and-matchmaking/room-archival and all four of its scenarios)

## 4. Enrolment, readiness, and the start gate (Convex — `packages/convex-snek-platform`, wrappers in `packages/convex-host`)

- [ ] 4.1 `enrolTeam` / `removeTeam` with set semantics enforced inside the transaction (racing-duplicate test) and no acceptance protocol on the team's side; assert by construction that removal cannot reach a launched game — no room mutation writes to an instance or to a launched game's roster (rooms-and-matchmaking/team-enrolment, team-enrolment#enrolment-is-a-set, team-enrolment#removal-never-reaches-a-launched-game). The bindings that make the latter true are game-lifecycle/roster-snapshot and global-invariants/game-instance-hermeticity
- [ ] 4.2 The mode gate on both mutations of 4.1, using the predicate of 2.3: an enrolment change addressed to a room that is playing is rejected in the mutation that handles the write — never merely hidden from the lobby — with the check inside the write's own transaction so an enrolment cannot slip past a launch starting concurrently. Tests: an enrolment and a removal rejected mid-play, an enrolment racing the initiation of 4.10, and an enrolment attempted *during* launch orchestration (the case a status-only check would miss, since the game is still `not-started` until the orchestration commits) (rooms-and-matchmaking/room-mode, room-mode#enrolment-refused-while-playing). The configuration half of the same freeze is game-configuration/launch-freeze's and is not re-implemented here
- [ ] 4.3 Same transaction, roster-side board invalidation: an enrolment change on the room's not-yet-launched current game clears any standing board designation and triggers the preview regeneration, committed with the enrolment rather than after it — with the test that matters being a start racing a late join, which must never consume a board generated for the old team set (rooms-and-matchmaking/team-enrolment#enrolment-change-clears-a-standing-board). The lock flag, its clearing rule, and the regeneration itself are game-configuration/board-preview-lock-in and game-configuration/board-preview; what this capability owns is that an enrolment write is one of the events that triggers them, and that it is the same transaction — agree the call shape with `migrate-game-configuration` before writing either side
- [ ] 4.4 Reject enrolling an archived team, reading the archived state team-management/archive-not-delete owns (rooms-and-matchmaking/team-enrolment#archived-team-cannot-enrol)
- [ ] 4.5 The archive-side withdrawal: archiving a team removes it from the enrolled set of **every** room it is enrolled in, written in the transaction that commits the archival so no observable state has the team archived and still enrolled — and routed through the same enrolment-change path as 4.1 and 4.3, not a second write, so the board consequence of 4.3 fires for each room that is configuring. Stated with no qualifier because none is needed, not because the wider set was wanted: a team can only ever have been enrolled while its room was configuring (4.2), so for every room an ordinary start produces the two candidate scopes coincide. The withdrawal is the **one** enrolment change the mode gate of 4.2 must let through, and the only case where that matters is an override-seated launch that left an enrolled team unseated — reachable, so test it: a playing room whose game did not seat the archived team drops the enrolment and its launched game is untouched. Test also the multi-room case and the board-clearing case (rooms-and-matchmaking/team-enrolment#archiving-withdraws-the-team-from-every-room, team-enrolment#the-withdrawal-clears-a-standing-board-too, team-enrolment#removal-never-reaches-a-launched-game, room-mode#the-withdrawal-is-the-one-change-a-playing-room-admits). Seam: the archival mutation itself is team-management/archive-not-delete's — agree with `migrate-team-management` whether it calls into this capability's enrolment path or this capability exposes a withdrawal the archival invokes; either way it is one transaction and the enrolled set stays this capability's to write
- [ ] 4.6 Negative test pinning the simplification the author chose: no archived-team condition anywhere in the start gate, and the state that would need one is unreachable by two independent routes — a competitively engaged team cannot be archived at all (team-management/archive-not-delete#archived-and-playing-is-unreachable, resting on team-management/roster-freeze through the not-frozen precondition), and a team archived while merely enrolled is withdrawn by 4.5. Assert the gate reads no team's archived flag at all, so the removed condition cannot creep back in as a defensive check (rooms-and-matchmaking/game-start-gate, team-enrolment#archiving-withdraws-the-team-from-every-room)
- [ ] 4.7 `declareReady` / `retractReady` on the **game** record, authorized to the enrolled team's current captain only — resolved from team-management/team-record — and retractable for as long as the game is not started (rooms-and-matchmaking/team-readiness, team-readiness#captain-only-even-for-insiders, team-readiness#retractable-until-start)
- [ ] 4.8 Freshness-as-clearing test: a successor game created by game-lifecycle's auto-creation begins with every team not ready — readiness is never among the fields a successor inherits, so no sweep exists to forget (rooms-and-matchmaking/team-readiness#stale-readiness-never-survives)
- [ ] 4.9 Decide and record the initiation boundary: which mutation constitutes "initiation", how the two-record gate (room enrolment, game readiness) is evaluated in the same transaction that commits the initiation, and how that transaction hands off to game-lifecycle's launch orchestration action. The legacy shape put these preconditions inside the orchestration action's opening mutation; whichever shape is chosen, record it as this change's design rationale (rooms-and-matchmaking/game-start-gate#gate-checked-at-initiation-not-in-the-surface)
- [ ] 4.10 The gate itself: administrative actor only, at least two enrolled teams, readiness unanimous over the whole enrolled set, room not archived — with tests for a third unready team and for readiness retracted between surface enablement and arrival of the initiation (rooms-and-matchmaking/game-start-gate, game-start-gate#unanimity-over-the-whole-enrolled-set, game-start-gate#gate-checked-at-initiation-not-in-the-surface). Explicit non-work, owned by game-lifecycle/launch-orchestration and launch-gates (and by tournaments for the override arm): config freeze, health gates, invitations, abort, walkover — passing this gate is necessary, never sufficient
- [ ] 4.11 Keep the gate off the schedule-bound path: the start a competition format performs on a room it governs must not route through this gate at all — a test asserting a format-governed room offers no start affordance and that its games begin with no readiness consulted and no user initiation recorded (rooms-and-matchmaking/game-start-gate#a-scheduled-start-does-not-consult-this-gate). The scheduling itself belongs to the format's capability, not here

## 5. Room-facing surfaces (web client — `apps/centaur-server-reference`)

- [ ] 5.1 `/rooms` Room Browser: listing with name search, per-room owner-or-ownerless state, enrolled-team count, playing indicator, link to each room's lobby, and the room-creation affordance (rooms-and-matchmaking/room-discovery, room-discovery#hidden-is-not-gone). Also check the sibling surfaces being built for a competing platform-wide live-games listing — accounts-and-profiles/home-view is user-scoped by its own text — and flag any that break the browser's sole-discovery-surface scope (room-discovery#live-games-found-through-the-browser)
- [ ] 5.2 `/rooms/[roomId]` Room Lobby shell readable by every authenticated user: owner-or-ownerless state, enrolled teams, per-team readiness, and — mounted rather than reimplemented — the configuration surface for the room's current game, reading that game's own record (rooms-and-matchmaking/room-lobby, room-lobby#lobby-shows-the-current-games-own-values, room-lobby#unaffiliated-viewers-see-everything-touch-nothing)
- [ ] 5.3 The lobby's actor mapping, which is this capability's to own because the configuration component has no actor vocabulary: compute the three mount-time affordance-kind parameters from the viewer's relationship to the room — inspection for every viewer, parameter editing and board designation for the administrative actor only — and pass them in, deriving nothing about actors inside the component (rooms-and-matchmaking/room-lobby#the-lobby-supplies-the-actor-mapping, room-administration). The kinds themselves and the mount-time parameter per kind are game-configuration/host-selected-affordances; a test should assert the two mountings differ in nothing else
- [ ] 5.4 Affordance-gating mirrors, each mirroring a server-side rejection rather than substituting for it: administrative affordances exclusive to the administrative actor (rooms-and-matchmaking/room-administration), readiness toggling exclusive to the captain with a read-only indicator for everyone else (team-readiness#captain-only-even-for-insiders), and the disabled start naming the unmet precondition (game-start-gate#disabled-start-explains-itself). Add the mode mirror here too: while the room is playing, the lobby offers no enrolment affordance and says the room is playing rather than presenting a control the mutation will refuse (rooms-and-matchmaking/room-mode#enrolment-refused-while-playing)
- [ ] 5.5 Treat the remaining lobby regions siblings own as integration slots in this shell and agree the composition boundary with their changes — the nominated-server healthcheck ping (team-server-management) and the live-spectate link for a playing game (live-game-observation). The configuration region is no longer a set of slots to compose: it is one self-contained component this shell mounts (5.2–5.3), and none of its internals is work in this change (rooms-and-matchmaking/room-lobby)
- [ ] 5.6 Flag to the author before building 5.1–5.5: the Room Browser and Lobby are platform-wide surfaces, and the only home for them in the package map is `apps/centaur-server-reference/`, the forkable Centaur Server reference app teams may modify freely. Confirm that is the intended home for the platform's sole discovery surface, or that a platform-owned deployment of it is what players use (rooms-and-matchmaking/room-discovery, room-lobby)
